# Agent workflow

Reusable workflow execution and iteration infrastructure extracted from self-media. On 2026-10-04 the user confirmed that general execution, PostgreSQL asset-management harness, general Agent SDK adapters, evaluation/comparison/history, and a reusable workbench belong in this shared project. Consumers such as creation supply domain workflows, tools, asset schemas, evaluation criteria, and specialized readers; do not require each consumer to rebuild the common infrastructure. Start with docs/product.md, docs/architecture.md, and docs/harness-roadmap.md for scope and implementation status.

Keep these capabilities modular. Core must not import a provider, PostgreSQL, SQLite, a UI, or a consumer repository. General persistence, runners, services, and UI belong in separate adapters/modules. Current shared packages provide core, PostgreSQL workflow-run storage, a read model, schema/storage contracts, the Workflow Space service/runtime/console, `@signal-room/workflow-skill-snapshot`, and an official OpenAI Agents SDK runner with a bounded SIWC Responses model transport. The official `@openai/agents` SDK owns the Agent turn/tool loop; the custom `Model` sends requests over the ChatGPT-authorized Responses route. This does not claim support for the complete Agents SDK surface, every deployment variant, or native session resume. SQLite is not an execution-store option: legacy SQLite data may only be handled by an explicitly invoked, read-only migration/import path. Legacy Codex traces are read-only evidence decoded by `workflow-read-model`; they are not an execution fallback. The PostgreSQL package remains a bounded persistence surface, not the complete asset harness; the production shared workbench remains incomplete. One Workflow Space represents one business purpose and aggregates its workflow versions, runs, assets, configs, reviews, and iterations; the asset console is scoped to that Space. See docs/space-storage.md for current APIs and limits, `docs/postgres-storage.md` for the implemented surface, and `docs/harness-roadmap.md` for current gaps. Keep domain methods and research skills in consumers. Inject filesystem/runtime configuration into adapters. Preserve persisted run/step/artifact formats and replay fingerprints unless a documented migration is provided. Do not use SQLite/Codex runtime paths as compatibility fallbacks for new execution. Temporary VM orchestration is out of the current scope.

Run `npm ci`, `npm run verify`, and `npm run example` before releasing. Changes are shared across projects: commit and push this repository first, then explicitly update each consumer's submodule pointer. Do not install global skills or include runtime traces, credentials, databases, or research assets.

For workflow authoring, use the guides in docs/ and the runnable examples in examples/. Keep documentation aligned with the checked-out API.
