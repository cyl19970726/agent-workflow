# 从业务理解形成可检验的方法

本 skill 仅属于 `vendor/agent-workflow` 项目。使用共享 [Operator CLI](../../../docs/operator-cli.md) 和宿主已认证的 Space；不要安装、链接或注册到全局 skill 目录。首版设计是可检验的方法假设，不能把草案、登记、可执行、已运行、已验证和已采用混为一种状态。用户通过对话表达修改意图，Agent 使用本 skill 与 CLI 操作，前端用于阅读、判断和准确回查；编辑表单属于次要入口。方法与预期产出等 HTML 图复用宿主已有 Archify 集成及可点击职责详情，不另造 HTML/SVG 查看器。

## 先完成专业判断，再组织 Agent

先执行 `understanding`，记录准确修订 ID 与 `payloadHash`。必要时用 `understanding-history` 和 `understanding --revision ID` 恢复形成过程；业务目标需修订时使用 [space-business-understanding](../space-business-understanding/SKILL.md)。核对原始请求、材料及 Case，区分长期业务、这一版方法和一次任务。旧方法只是有适用范围的经验；新 Space 不自动继承旧设计或结果。

从交付给实际使用者的成果反推专业工作。找出最容易“看似做完却没有兑现价值”的判断，选一个代表任务和一个足以改变做法的困难情形，实际处理这些判断，留下可读的小样、证据和取舍。先发现怎样做好工作，再决定用几个 Agent；不要把“研究→撰写→审核”等熟悉角色当作已论证的方法。

关键做法应让执行者知道：判断什么、取什么证据、怎样辨别冲突或不足、如何制作和检查成果、交给下游什么。可选择领域 skill、参考材料、Prompt 或工具，但需说明其实际提供的能力及缺口。不要为了“完整”同时装载所有专业资料，也不要用更多禁令或更长 Prompt 替代工作方法。资料中的主张、自己的推论、用户选择和待检验假设分别保留。

在走查中比较一个合理替代：为何合并或分离职责、哪些信息独立检查者不该看到、哪些资产值得单独保留或返工、这样增加什么代价。结构不必固定为流水线或多 Agent；程序能够可靠完成的转换，不必再交模型。设计 Agent 自己做的小样属于设计证据，不算 workflow 的实际产物；外部提供的答案或审阅修正也应注明。

## 将方法落到可执行的交接

沿选中的资产路径，核对下面几组关系；完整设计维度与示例见 [设计指南](../../../docs/designing-workflows.md#设计-agent-与工作流设计包)，无需复写成另一份长清单。

- **判断与能力：** 节点要完成什么专业判断；实际 Prompt／可选 skill、模型配置、工具或程序在哪里承担它。模型选择根据任务难度、成本与实际试做，不从旧宿主默认值推导最优。
- **上下文与证据：** 节点实际获得哪些准确输入、来源和前轮反馈，哪些刻意隔离；下游能否定位决定性证据、读懂单位／口径／不确定性。最终判断依赖例外或排除条件时，核实缺失字段的含义：未提供证据不等于已证明不存在；只有明确的数据合同或补证才能作这个转换。仅把上一份输出整包塞入下一节点不是交接设计。
- **工具与产物：** 核实工具确实存在，完整说明、输入、返回、权限和失败语义可读。输出须同时服务人阅读、下游判断及必要程序校验；可解析不代表内容正确，引用形式合法不代表指向真实来源。
- **控制与恢复：** 缺料、矛盾、工具失败、格式错误和业务不达标如何区分；什么可局部修复、什么应补证或停止；谁能作决定、修到哪一版、最多投入多少。重试边界与实际副作用相称。

保存关键决定到执行位置的对应：业务目标／依据 → 选择的做法与责任 → 实际指令／上下文／工具／程序／路由 → 可观察检查。允许人工实现或配置标准扩展接口；并不要求自然语言自动编译。但设计正文、图和执行定义出现差异时必须修复或标为不可执行，不能发布说明 A 而运行现成 B。

在看到结果前固定验证范围：材料与困难样例、关键和最终成果的判据、判者、要检验的假设、预算、停止条件及真实用户反馈的位置。优先检验最高风险节点与交接；只在授权和明确预算内使用候选的真实指令、上下文、工具试做，不能为满足预算暗中剥离正式能力。区分节点尝试、工具调用与实际模型请求；工具接续和技术修复是否消耗请求配额、计时从何时开始必须明确。保存原响应，不临场代写后算节点通过。程序检查、专业审阅、独立阅读、实际 Case 和业务接受各自说明能支持的结论。

## 形成设计包并通过 CLI 保存

设计包组织现有对象，不新造一套真相：准确业务理解与设计说明；同一候选的 Archify 方法／资产图及节点详情；实际执行定义与验证方案。正文应能独立解释这版兑现什么、为什么这样工作、替代与未知，具体配置通过准确对象引用。细节按需展开，不让配置和校验记录淹没业务主线。

空白 Space 宿主的已实现命令、请求示例与能力边界见 [当前操作合同](references/operator-contract.md)。先读此合同，避免将旧宿主能力当成新 Space 能力。

先确认目标 Space 和宿主可用能力，最新操作合同见 [Operator CLI](../../../docs/operator-cli.md#方法能力设计草案与准确候选)。形成专业能力后，优先用 `capability-prepare` 准备请求，再用现有 `capability-save` 保存；设计说明用 `design-prepare` 准备，再由 `design-save` 保存。具体输入与参数见 [当前操作合同](references/operator-contract.md)。Agent 负责专业正文、选择与改动理由，CLI 负责机械引用、原文字节 hash、认证署名和提交依据；不再临时写脚本组装这些字段。准备只生成本地可审阅请求，不登记方法或运行模型。

审阅准备结果时，重点判断所引用的业务理解、能力与前驱是否正是本次想修改的依据，以及实际内容差异是否兑现改动目标。显式选择的历史依据不能被自动换成当前版本；并发冲突后要重新判断，不能借自动取最新绕过。可用工具、上下文和路由仍受宿主具名 provider 合同约束，准备请求不创造新执行能力。旧宿主不支持准备命令时，可按操作合同使用原有 save 请求。

准备好的请求保留准确依据与幂等键。保存结果未知时，先按原对象核对，再用完全相同的请求重试；改变内容或依据时形成新的准备请求，不覆写原意图。保存新增不可变修订，仍为 `unconfirmed`。凭据使用宿主受信设计 Agent 身份；所有文件参数用绝对路径，私有业务内容不进入公开文档或 Git。

保存后执行 `design`、`design-history` 或 `design --revision ID`，读回正文、理解／能力引用、来源、署名和前驱。使用 `design-definition --revision ID` 核对完整候选的 `candidateId`、冻结依据、实际指令／输出合同／工具／上下文／路由／预算和执行阻碍；`method-preview` 的短摘要不代替这一步。专业指令若由 provider 追加 schema 等内容，核对完整最终指令和转换依据，不能只比原始文案。读取接口若返回脱敏、深度截断或摘要，只能作阅读投影，不能直接复用为执行 schema／指令；从受支持的完整导出或准确源码取得合同，核对内容 hash，并先通过实际合同校验器。没有完整读路就标明发布前一致性检查受阻。

固定的设计与能力修订仍可能由变化中的 provider 实现重新编译出不同候选；不要将草案 ID 当作永久不变的执行定义。登记前重新读取候选并校验期望 ID，实现变化须重做受影响检查；登记后的准确版本才保留执行定义。预览不运行模型也不登记，可用性不等于发布、运行或验证。

在任务已明确授权登记且完整候选与设计一致时，执行 `method-publish --design ID --expected CANDIDATE_ID`，其中 ID 取当前完整候选的原值。发布是独立写操作，需要宿主同源、会话绑定 CSRF 与明确授权；受信设计 Agent 仅经宿主限定委托登记本人、本会话保存的准确候选，不自行获得一般 owner、运行或采用能力；没有这项授权时保留可审阅的草案与预览。登记不扩大执行、评价、采用或外发权限。首版／后继版能力按宿主实际合同执行；支持后继版时记录准确前驱与行为差异，不伪造另一首版或借改名绕过限制。

登记后执行 `method-basis VERSION_ID`，再读 `version VERSION_ID`、方法与产出图及关键 `node VERSION_ID NODE_ID`。核对冻结设计、当时业务理解、方法身份、入口、节点职责、预期资产与交接一致。之后业务理解即使更新，原版依据仍保持准确；旧版缺失依据就标明缺失，不用现时推论补造。

## 独立读回与后续修订

验收工作台或新交互时，从普通前端入口完成接手任务：理解目标和理由，点击 Archify 节点／资产读取专业做法及实际配置，追到准确依据和验证方案，返回并重开同一范围。先自己使用，再按风险请未读设计答案的 Agent 独立复原；之后用 CLI 核对同一事实。打不开、读不懂或只能靠作者解释的地方仍属缺口，不能以接口有数据通过。日常方法修订按受影响内容核对，不要求每次重复完整双通道产品验收；用户明确要求的阶段实用验收仍需完成。

交付分别报告草案、登记、部署可执行、节点试做、真实 Case／评价与采用状态。方法变化须指向具体行为差异及旧版，重做受影响检查；不要为展示版本树制造无业务意义的候选。实际失败先区分本次成果、材料、专业方法、评价者、harness 和执行环境，再决定修改对象。

记录设计 session 的原始输入、关键决定和输出引用供改进设计 skill；workflow trace 用于判断本方法实际怎样工作，两者不互相抵扣。复杂 skill 改动可用未透露答案的不同约束任务做有界迁移检查，保留产物和遗漏，不将一题通过当作普遍有效。后续按 [建设与验收路线](../../../docs/harness-roadmap.md#从空工作台验收设计能力) 接续，不因本 skill 自动扩大运行、采用或外发权限。
