# 评估一个 workflow 是否值得信任

前置阅读：[设计 Workflow](./designing-workflows.md)。本篇回答“结果有没有满足用户意图，Evaluator 的判断是否可信”；得到证据后进入 [优化 Workflow](./optimizing-workflows.md)。Evaluator 与 workflow 都从同一版意图和成功标准推导，不从已有步骤倒推全部判据，以免二者同时遗漏同一项需求。

`workflow` 的状态、Schema 校验和流程内 Reviewer 回答的是不同问题。执行成功只说明步骤按合同结束；Schema 有效只说明数据形状符合合同；业务 Reviewer 只对它审阅的某个产物版本给出意见。三者都不能单独证明这个 workflow 能稳定地产出完整、准确、可用的结果。

评估 workflow 时，把它当作一个待测系统，把评估器当作一套独立的测量装置。评估装置记录被测版本、冻结输入、来源证据、判断方法和最终裁定；它不改写生产运行的状态或报告。生产流程内的 Reviewer 可以成为被测系统的一部分，也可以被单独拿出来评估，但不能同时充当唯一的验收依据。

```text
冻结案例 + 被测 workflow 版本
              │
              ▼
       普通 workflow runs ──── 执行物证、产物、用量、耗时
              │
              ▼
    独立 evaluator / oracle ── 质量判据、证据覆盖、错误、盲点
              │
              ▼
      按授权范围裁定 ──────── 保留 / 修复 / 再测 / 晋升
```

## 先写清楚要证明什么

在运行模型前，先写出一个可被反例推翻的主张。例如：“新 Reviewer 能发现旧 Reviewer 漏掉的、画面中清楚可读的产品名。”这比“高推理模型更好”更容易验证，也提醒团队不能从一个案例推广到所有任务。

评估计划至少说明：

- **被测对象**：workflow ID 与 revision；必要时包括 Agent 定义、prompt/skill 快照、工具和运行时版本。
- **评估对象**：完整端到端流程，或其中明确的一段，例如 Builder、Reviewer、恢复策略或工作台阅读体验。
- **成功判据**：事先确定的可观察结果与可接受边界。将内容质量、执行可靠性和效率拆开，不用一个总分遮盖失败。
- **证据与裁定者**：确定性校验、独立来源/人工标注、盲审，或这些方法的组合。记录评估者的版本和限制。

输入应来自设计报告中的意图/验收对应表，同时包含约定交付节点、输入与方法版本、案例、预算和允许的复用范围。尚无历史基线时只判断是否满足标准，不生成虚构的改善幅度。

## 先校准 Evaluator，再解释它的分数

“独立”既指调用/上下文隔离，也指判断有外部依据。同一作者写答案再写评分器，即使函数分开，也可能共享同一个盲点。人工标注、源材料和其他 Reviewer 也可能有错；保留争议、出处与裁定责任，不把多数投票视为真值。

先准备一组与任务相关、已有来源依据和独立裁定的校准案例。它用来检查 evaluator，不能泄露给正在被测的 Builder。下面是校准类型，不是新增的通用质量 Gate：

在看校准结果前，按任务风险写明允许的误报/漏报范围、关键缺陷不能漏检的条件、最低案例覆盖和不可判时的处理。没有统一适合所有任务的数值；边界应对应用户约束及判定用途，不能看到结果后临时放宽。样本不足以支持边界时，校准结论就是证据不足。

| 校准输入 | 预期判断 | 检查什么 |
| --- | --- | --- |
| 已裁定正确的产物、合理同义表述 | 不因字面不同报错 | 误报和语义理解 |
| 有来源支持但不在必答清单里的额外内容 | 不直接当作无依据 | 必需覆盖集与允许事实集是否被混为一谈 |
| 删除关键结论、改错数字或挂错证据的副本 | 指出具体缺陷、位置与依据 | 漏检、证据绑定和严重度 |
| 缺少决定性来源或存在未裁定冲突 | 明确不可判及缺什么 | 是否为了交分数而猜测 |
| 无产物的断流、无效 evaluator 输出 | 记录执行/评估失败 | 是否伪装成零 finding 或质量通过 |

缺陷副本只用于隔离校准，不能覆盖真实资产。预置缺陷只覆盖已知错误类型，需要补真实漏项、正确反例及未见案例。对已裁定缺陷计算检出与漏检，对正确案例计算误报；完整标注不足时只报告已标范围，不能用未标记等同正确。

固定 evaluator 方法、模型、工具与版本，在重要案例上重复或调换候选展示顺序，记录不一致项和审阅投入。检查实际来源读取与引用：已交付整包 skill 不等于已读相关指导，读取命令成功也不等于输出未被截断。Trace 用于解释过程，真正看过某帧也不能单独证明结论正确。

校准失败先修 evaluator，结论不足则暂停相关判定；不用无限叠加“审阅审阅者”。由原始证据、可复核标注和明确的争议裁定形成有限闭环。Evaluator 不知道新旧版本身份和预先缺漏清单，但必须获得判断所需的意图、来源和产品约束；盲审不能以剥夺必要上下文实现。

## 做可解释的对照实验

对照实验的关键不是一定要随机分组，而是把不同条件下的证据做到可比较。

1. 选取有代表性且可复核的输入案例。冻结输入文件、证据包和引用版本，计算摘要；不要让一个版本读到另一个版本的产物或评语。
2. 选择基线与候选版本。除待检验变量外，尽量保持输入、评估规则、工具条件和运行方式一致。若同时换模型、prompt、skill 和数据，就只能判断整体变化，无法定位原因。
3. 同一批案例分别运行两种条件。模型有随机性时，对重要结论重复运行并报告波动；运行成本或风险太高时，清楚标注样本量和不能推广的边界。
4. 让 evaluator 不知道版本身份，也不把 Host 预先发现的问题直接泄露给它。这样可以观察它能否独立发现问题，而非复述提示。
5. 将双方产物绑定到实际 run、attempt、候选 SHA 和输入 SHA，再逐条比较命中、误报、漏报、证据正确性和执行代价。意见数量不是质量分数。
6. 由独立来源或人工裁定争议项。把 evaluator 自己的错误也纳入记录；必要时先评估 evaluator，再用它评估 Builder。
7. 在未参与调参的 holdout 案例上复测。只有验证过的范围才能晋升；出现失败时，保留案例成为之后的回归集。

完整的假设、归因、对照选择和采用条件见 [优化指南](./optimizing-workflows.md)。开发案例供调整方法，校准案例供核对 evaluator，最终验证案例保持未参与调参；同题已知答案留在评审侧。人工介入和后来新增的提示也属于实验条件。

[`examples/workflow-experiment.mjs`](../examples/workflow-experiment.mjs) 目前仅是确定性评分结构演示：Runner 按案例返回硬编码答案，`sourceSha256` 是占位标签，并未校验源文件。它用精确字符串集合匹配，candidate 的优势是预设的；没有实现语义评估、evaluator 校准、盲化或优化决定。它能运行不表示本指南的完整机制已经实现，更不能当作模型基准或真实内容质量判据。

## 不要把所有结果折叠成一个分数

至少分别报告以下维度，并为每个维度注明分母、样本范围与未知项：

- **执行可靠性**：启动、完成、超时、取消、子流程失败、恢复是否正确。模型断流、校验拒绝和内容 finding 是不同失效类型。
- **产物质量**：事实/内容覆盖、证据绑定、无依据结论、关键未知项、结构和下游可用性。结合严重度与漏检，不能只数 Reviewer findings。
- **Evaluator 质量**：对独立裁定或预置挑战案例的发现率、误报、证据准确性、稳定性与盲区。Reviewer “无意见”本身不等于全对。
- **代价和效率**：端到端时长、模型调用数、重试和修订次数、已知 token/费用。工具累计输入可能含缓存和多次请求；缺失数据标未知，不报零。
- **实际使用体验**：人能否从界面找到当前版本、来源证据、等待原因、可行动问题及已知限制。页面显示完成度不是内容有效性的代理指标。

用户投入也是代价：记录重复解释、诊断、提供修法、审阅及接受的实际事件，时间未测就记未知。结果合格与 Agent 自主完成是两件事，不能把用户提供的答案归为方法自主发现。

先展示原始计数与样本，再说明比率和区间。小样本可用于发现机制问题，不能支持总体稳定性结论。遇到一个关键失败也不能被大量无关成功平均掉。

## 评估失败也要可解释

一次评估可能得到“通过”“发现质量问题”“执行未完成”或“证据不足/评估器失败”。这些结论不可互换：

- **执行失败**：被测 workflow 没有形成可评估的产物；记录在执行面，不评分为内容错误。
- **质量发现**：有可读取产物，Evaluator 指出问题；候选继续保留并按产品政策修订或阻塞。
- **Evaluator 失败/不充分**：Reviewer 超时、断流、未绑定版本或证据读取不完整；不能当作“没有发现问题”。
- **评估通过**：仅表示预先写明的判据在指定案例、指定版本、指定证据范围内通过。它不是对未测范围的背书。

改 workflow 时不要覆盖旧 run 或事后补写历史结论。新版本生成新 run 与新评估；旧结果保持可追溯。若评估本身也通过 agent-workflow 执行，它应是独立的 evaluator workflow，输入引用被测 run 和不可变产物，而不是偷偷改写被测 run。

## 交付逐项结果，再决定是否优化

在项目主报告中维护一份当前评估记录，详细证据引用原处。下面是记录格式建议，不是已导出的 SDK 类型。

| 意图/验收项 | 被测版本与执行 | 检查与证据 | 判定及限制 | 后续动作 |
| --- | --- | --- | --- | --- |
| 关联设计报告中的要求，注明重要程度 | workflow revision、输入摘要、run/attempt、产物摘要、evaluator 版本 | 实际比较的内容、来源位置、校准依据及判定者 | 满足 / 未满足 / 不可判 / 未执行，说明覆盖范围 | 保留 / 局部修复 / 方法实验 / 补来源 |

执行未完成的案例仍计入整体可靠性分母；可评估产物比例另报。局部检查可以继续，但不能从仅成功的少数样本推导全流程通过。工作台可用、单份产物合格和方法在多案例有效分别报告，用户局部接受不自动升级其他维度。

校准可用、版本绑定准确、约定检查有证据且范围明确时，才能形成有范围的接受意见。发现问题交给 [优化指南](./optimizing-workflows.md)做归因和实验；缺输入回到 [设计指南](./designing-workflows.md)的对应步骤。到约定交付点就结束本轮，未覆盖项目保留未验证，不因流程图还有后续步骤自动扩展授权。

## 本仓库目前的边界

现阶段推荐从指南、冻结案例格式和可运行示例开始。宿主负责数据集、来源权限、模型服务、调度、评分/人工裁定、保密与展示。共享执行内核保持通用，不内置某领域的“正确答案”或通用质量分数。

跨多个消费项目验证出稳定共性后，再考虑增加可选的通用评估合同或适配器，用于关联实验、案例、执行和报告。未来合同至少要绑定 workflow revision、输入摘要、评估规则版本、被测 run/产物摘要、evaluator 身份、逐项证据与限制；评估记录必须独立于生产状态，支持部分结果、争议和不可判定。不要为了这份指南先增加一套第二调度器或把 `succeeded` 偷换成质量通过。
