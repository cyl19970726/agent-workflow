# Workflow Space 工作台：产品与交互定义

本页是**现行工作台产品定义**。产品目的与生命周期见[产品](product.md)，技术包边界与通信见[Space 前端架构](space-frontend-architecture.md)，批次验收见[前端实施计划](space-frontend-implementation-plan.md)，已实现与未完成以[建设状态](harness-roadmap.md)为准。2026-10-06 用户明确：完整流程图使用 Archify，作为注意力中心；点击节点及资产查看详情。下文是建设与验收合同，不是交付完成声明。

## 产品定位与本轮纠正

这是以 Space 为单位，**用 workflow 完成业务，并持续改进做事方法**的工作环境。人和 Agent 共用方法、资产、执行与评价事实；CONTENT 是第一个领域适配。它同时服务日常业务操作者、资产使用者和方法改进者，同一个人可以切换这些任务。只支持构建流程或查看历史记录，都不足以完成产品目标。

此前设计把结果阅读放在主要位置，再逐次补流程图、版本、执行和评价页面，形成了多个可以访问却难以连续使用的页面。2026-10-06 的实际审查确认：版本名难以区分、Case 的运行没有清楚关联方法、资产选择器使用“资产 1”等标签、迭代页无法展示已有版本与验证计划。局部工程通过不足以宣布整体工作台合格。

本轮改变信息架构和主交互方式：**图是主工作区，用户任务决定先看案例还是方法，资产与详情随选择展开。** 2026-10-07 用户指出当前页面仍偏向方法、run 和节点选择，缺少按真实选题查看输入与成果的一等入口。本页据此修正默认入口和案例阅读重点；这是待实施的产品要求，不是前端完成声明。

## 用户来这里要完成什么

先按任务设计，再决定信息放在哪里。以下是完整产品范围；具体能力是否已实现仍查[建设状态](harness-roadmap.md)。业务工作与方法改进共享证据，但用户做一个选题不需要先建立 A/B 实验。

| 用户此刻想做的事 | 必须获取的信息 | 要能完成的操作与结果 | 主要入口 |
| --- | --- | --- | --- |
| 弄清业务怎么做 | Space 的目标与标准；当前采用的方法；全流程、输入输出、责任与停止规则 | 看全图，检查节点，明确这一版适合做什么 | 工作流工作台 |
| 开始一项真实业务 | 业务要求、材料是否齐全、可用方法、执行条件与影响 | 建业务案例，挑选／导入材料，冻结本次输入，显式启动 | 业务工作台；图上也可发起 |
| 处理正在发生的工作 | 哪些在跑、停在哪、有哪些待处理事项、已有产物与下一步 | 到准确节点补充材料／反馈、取消或执行系统确实支持的后续动作 | 业务工作台的工作队列 → 工作流画布 |
| 审阅并交付结果 | 本次候选、前版差异、对应意见、未解决问题、是否已被接受 | 阅读／评价，明确选择交付版本，复制／下载或交接；留下交付反馈 | 业务案例结果区；资产详情 |
| 查找并复用已有东西 | 资料／中间产物／成果的内容、身份、版本、来源、适用范围、被谁使用 | 检索、并看、比较、导入新版本、加入下一个 Case 的输入 | 资产工作台 |
| 判断方法到底有没有变好 | 多个案例的结果与失败、条件差异、四问、改动依据与未知 | 记录问题，提出修改，发布新版本，建立验证，比较并决定采用 | 工作流内运营观察／演进视图；按需审阅队列 |
| 解释为什么这次这么做 | 冻结节点定义、实际配置与输入、工具／会话事件、费用与耗时的可用记录 | 从异常或结果定位原因；区分材料、方法、模型和基础设施问题 | 图上执行详情；运行记录辅助视图 |
| 沉淀下一次要用的经验 | 哪些观察已验证，适用什么条件，关联什么证据 | 保存有来源的结论和标准，明确装配进未来哪些节点 | Space 知识与配置辅助入口 |

两条业务闭环都必须成立：**要求与材料 → 执行与协作 → 结果审阅 → 交付与反馈**；**发现问题 → 查证与假设 → 修改方法 → 多案例验证 → 采用或继续改进**。资产、历史与评价连接这两条闭环，不能只做第二条的实验后台，也不能只做第一条的成果列表。

## 整个 Space 的工作台分工

工作台是同一个 Space 的不同工作视角，共用对象、权限、阅读器和操作接口；切换工作台不复制数据，不另建一套业务状态。

生命周期和所需决定先于菜单。主要入口按工作目的命名为“案例与产物”“工作流开发”“资产库”；CONTENT 的“案例与产物”可以显示为“选题与产物”。2026-10-06 的“业务、工作流、资产”是此前名称，现有路由可继续复用，改名本身不代表工作路径已经做成。**“工作流开发”是可展开／收起的工作流标题**，单一 CONTENT 时可直接标为“工作流 · CONTENT”；展开后提供贯穿完整生命周期的任务入口，具体合同见下节。评价贯穿被评对象，方法演进留在这个工作流下；有独立、持续的跨案例待审任务时，再开放专门审阅队列。

| 工作台 | 注意力中心 | 负责的工作 | 与其他工作台的连接 |
| --- | --- | --- | --- |
| **案例与产物** | 真实题目列表；案例内的关键输入、成果和形成关系画布 | 从请求到结果组织实际工作；发起、跟进、协作、审阅、交付与反馈；一个 Case 可有多版方法和多次尝试 | 按需展开中间成果；点生产过程进入准确方法；点结果复用统一资产阅读区 |
| **工作流开发** | Archify 画布，含方法／执行／运营观察／演进视图 | 从业务目标、设计理由和首版方法，到案例诊断、候选研发、多案例验证与采用；在节点与资产处读证据 | 从具体案例问题进入；验证后返回日常业务使用；方法全图可独立查看 |
| **资产库** | 资料与产物的内容、版本及关系 | 跨案例查找、阅读、对照、复用；管理来源、修订和归属；发现尚未被运行引用的材料 | 从资产定位生产节点和使用它的运行；把准确版本选入新的输入清单 |
| **评价与迭代能力** | 工作流内的演进画布、各对象旁的评价及按需审阅队列 | 聚合四问与反馈，查看版本演进、验证集合、比较、未解决问题和采用依据 | 从版本边回到问题与验证，点版本返回完整方法；不把评价迁离其被评对象 |

Space 外壳持续提供目标与标准、搜索、待办／运行提示及配置入口，不再为每一种数据库对象都增加一个一级菜单。会话历史属于节点执行证据；Agent 定义与工具配置属于方法；长期知识与权限属于 Space。需要跨运行排障时提供运行记录视图，不要求日常业务操作者先进入技术日志页。

“业务”是共享语义，CONTENT 可显示为“选题与创作”，其他业务可改为“客户任务”等。Case 既可用于真实业务也可用于验证，不能在没有记录时自动判定其用途；验证计划引用 Case，不吞并 Case 的日常工作身份。本轮只实现单一 CONTENT 的这些视角，不扩张到 B3 或多个主业务 workflow 的调度。

## 共用什么与定制什么

| 层 | 共享 agent-workflow 提供 | 业务 workflow 提供 |
| --- | --- | --- |
| 对象与事实 | Space、版本、Case、manifest、run、节点实例、准确资产、会话、评价与采用 | 业务目标、案例内容和结果要求 |
| 方法与执行图 | 同一流程合同的 Archify 视图、节点选择、实例状态与实际路径 | 节点、控制边、端口、停止／返工规则及可验证映射 |
| 信息架构 | Space 外壳、版本／案例选择、资产阅读、关系与迭代入口 | 节点与资产的可读名称、主产物／支持材料／审阅等业务角色 |
| 阅读与比较 | 可序列化阅读模型、通用组件、版本和证据定位、未知类型回退 | schema、阅读器、比较字段、来源与片段解析 |
| 操作 | 授权服务、动作可用性、准确对象绑定、提交回执 | 已部署的领域操作、输入表单与业务政策 |

资产 schema 决定正文结构；流程和存取合同决定由谁读写；展示契约决定人如何阅读。展示配置不能制造执行关系、给予权限或改变采用结果。共享前端由业务注册扩展，不为 creation 再做一套独立资产后台。

## 前端应该长什么样

先恢复用户上次明确的工作位置；首次进入已有业务的 Space，默认打开**案例与产物**，按真实题目看到关键输入、现有成果、处理状态和下一步。尚在初建、没有方法和案例的 Space，提供业务目标与首版方法入口。展开**工作流 · CONTENT**等工作流标题可直接选择下列长期任务；方法图在需要理解定义或执行时仍是中央主工作区，运营观察和版本演进使用各自准确的图语义。日常业务不要求用户先理解 run 和版本 ID，开发者也不必绕过成果列表才能看到方法全貌。

### 工作流标题下的生命周期任务

这些二级项是可以随时直接进入的工作入口，**不是要求逐项走完的向导**。已采用方法可以持续服务业务，候选方法可同时研发；一次作品修订也不必升级工作流版本。各项都从同一 Space 的方法、运行、资产和判断事实读取，Agent 的 skill 负责改法，CLI／tool 负责准确查询与持久动作，harness 负责执行与证据采集。导航组织生命周期，不会仅凭新增页面或标签实现设计、调优与稳定服务。以下是目标交互结构，当前前端尚未完成这组展开导航及各项完整任务验收。

| 工作流二级项 | 此刻要完成的任务与默认主体 | 关键动作与通往后续工作的关系 |
| --- | --- | --- |
| **目标与设计** | 明确业务目的、适用范围、成功标准、人的裁决边界及首版为何这样分阶段；默认看目的、设计理由与完整方法图，无首版时看可保存的设计起点 | 检查节点职责、输入输出、配置和关键假设，形成或修订可执行候选；经明确发布后可到“运行与案例”验证，未证实的设计理由保留假设身份 |
| **运行与案例** | 选择准确方法处理一个 Case，理解本次实际路径、节点状态、输入和产物；默认看所选 run 叠加的完整流程图，没有 run 时仍可看方法定义及案例入口 | 显式发起、跟进或处理系统支持的异常，点产物读准确资产；从问题进入“评价与调优”，从稳定可用的结果返回“案例与产物”做日常处理 |
| **评价与调优** | 判断本次作品和方法哪里好、哪里差、原因可能在哪；默认看所选产物、对应四问、执行证据和未解问题 | 区分补材料／修本次作品与修改方法；Agent 可经 skill＋CLI／tool 提出有证据、可推翻的改动假设，再到“版本与验证”检验，评价不自动产生新版 |
| **版本与验证** | 看清前驱、变更原因、候选与基线，判断改法在哪些案例改善或退化；默认看准确版本关系与冻结验证范围 | 发布候选、按条件运行并比较全部尝试及代价，记录采用、回退或继续查证；采用有明确范围后进入“稳定服务”，查看候选不改变生产采用版本 |
| **稳定服务** | 看当前采用版本怎样持续处理常态业务、适用什么范围，以及反馈、失败与人工成本；默认看采用范围内的案例／运行、关键阶段资产和待处理事项，不拼造单次执行路径 | 日常案例继续从“案例与产物”进入；可定位异常、收集反馈、处理或回退，积累有纳入规则的观察窗口后进入“复盘与再调优” |
| **复盘与再调优** | 在一周等明确窗口内判断方法是否仍值得使用、哪些问题反复发生；默认看窗口、样本与评价覆盖、阶段资产、反例及既有决定 | 保存继续使用、限制范围、回退或开启候选的有据决定；需改法时回到“目标与设计”或“评价与调优”，新候选另行验证，不自动替换稳定方法 |

版本是当前任务的选择范围：方法定义、单次运行、验证和运营观察各自明确“正在查看／当前采用／可执行”的准确版本，并按需选择其他版本；主导航不把每个版本永久展开成二级项。折叠工作流标题只收起导航，**不取消当前任务、不丢所选页面或对象**。当前二级项应可见；若导航收起，父标题仍标明当前任务。刷新恢复工作流、二级项及已选范围，指向二级项的深链接自动展开标题；返回案例与产物或资产库后，再进入时恢复该工作流上次明确的位置。

案例列表不是三个选择器：可读题目、输入摘要、当前成果及处理状态构成一项业务记录。进入案例后，默认画布突出“要求与材料 → 主要成果”，阶段产物就近可展开；点资产读正文，点生成或审阅关系读对应过程和意见。每个节点的预期输出类型在方法图上可见，实际已产资产在案例图上可见。失败案例显示失败阶段、已保存成果与可执行下一步，不能只剩错误信息，也不能把过程稿称为已完成终稿。Space 目的和待处理事项保持紧凑；检索和待办无需强行用图表示。

若首次进入时没有采用版，明确显示这个事实，同时提供可执行版本和已有 Case 的入口；正在查看的最新候选没有 run 时，不让空产物成为理解方法的起点。定义模式点节点默认读职责、模型／工具、输入输出及适用条件，运行模式默认读本次状态、轮次与产物。必需首轮材料、可选材料和返工才使用的前稿／意见按已声明合同区分；合同未保存时显示未知，不从 `priorDraft` 等字段名猜规则。

以下示意专指“工作流开发”中需要完整方法图的任务，不是所有用户进入 Space 的必经页面；运营观察和版本演进仍使用下文定义的准确范围与图语义：

│ 案例与产物           │ 正在查看：准确方法版本               │ 选中节点的职责    │
│ ▾ 工作流 · CONTENT   │                                      │                  │
│   目标与设计         │ 当前任务：运行与案例                 │ 或本轮执行        │
│   运行与案例         │                                      │                  │
│   评价与调优         │                                      │                  │
│   版本与验证         │                                      │                  │
│   稳定服务           │                                      │                  │
│   复盘与再调优       │                                      │                  │

### 工作流信息如何在画布内展开

“都能在画布里查看”指工作流相关信息都可从当前图触达，并在其阅读／操作层展开；不把所有长文、日志和资产同时铺在画布上。默认突出主路径，选择对象后再显示有关的信息、数据边与动作。主画布内没有必须跳到另一个后台才能查清的核心关系。

| 点击的对象或入口 | 画布内展开什么 | 绑定与操作规则 |
| --- | --- | --- |
| 版本标题／变更标记 | 完整方法身份、改动原因、前驱、采用情况、配置差异 | 更换查看对象不自动发布、采用或启动 |
| 入口材料／输入端口 | 所需 schema、实际绑定的资料、缺失项、冻结输入清单 | 定义模式是要求，执行模式是本次真实输入；补材料走明确新版本／新输入流程 |
| Agent／程序节点 | 职责、工具、模型、Prompt、输入输出定义；本次状态与有效配置 | 声明与实际分开；可从此定位修改，但不改写历史方法 |
| 控制边／路由节点 | 触发条件、停止／返工规则；本次有记录的判断与依据 | 允许路径和已发生路径分别显示，没记录就说明未知 |
| 节点的轮次／尝试 | 本业务轮的执行、失败、技术重试及产物 | 不把第三稿和第三次网络重试混在一起 |
| 资产／输出端口上的真实产物 | 正文、附件、版本、来源、去向、对应评价 | 支持扩大阅读、分屏对照、沿关系切换，并返回原选择与图位置 |
| 意见／评价标记 | 对这份资产的四问、标准、判者、基线与证据 | 可提交系统已支持的评价；打分不等于接受或采用 |
| 待处理／失败标记 | 原因、已有结果、所需输入及当前可执行动作 | 只有真实待处理记录才能显示待办；取消／续作／重试遵守当前能力与原动作边界 |
| 会话／操作记录入口 | 可获取的消息、工具事件、耗时与用量、缺失说明 | 搜索与定位到节点实例；敏感内容按权限过滤，不承诺模型内部思考 |

查看信息默认用侧栏；长文和对照可以扩展为覆盖层或分屏；与当前对象有关的小操作用紧凑表单。三者复用同一个对象选择状态。打开配置不默认摊开全 Prompt，展开长文不销毁图，打开会话不丢当前资产。加载另一对象前保留未提交的评价或明确提示其处理方式。

### Space 概览

Space 的默认进入规则见上一节。进入“工作流开发”后，显示上次明确查看的版本；没有记录时显示当前采用版本；尚未采用时可预览最新已发布版本，但必须清楚标注“正在查看最新发布，尚未采用”。没有方法时提供定义／注册入口，不假造示例作为真实状态。案例入口保留自身选择，不因开发视图查看了另一版方法而悄悄切换案例的真实结果。

标题栏始终区分**正在查看、当前采用、最新发布、是否有可执行部署**。版本有数据不等于仍能运行；不可运行时说明缺少匹配部署，不删除历史查看入口。独立判者等辅助 workflow 显示用途，在辅助分组下可找到，不与主业务版本混成一串技术 ID。

“当前采用”有明确作用域：由业务接入声明主方法身份／entrypoint 与所使用的方法采用 slot，标签说明采用的是哪项业务方法。Space 里可能同时存在作品资产和多种方法的采用指针，不能随意取一个 adoption head。未配置该语义、未指定采用，或存在未解决冲突时，分别显示原因；不按最新时间、标题或模型推测主方法和辅助判者用途。

版本列表至少显示可读名称、修改原因、前驱、时间、执行可用性、案例／运行数量及评价覆盖。准确 ID 保留为可展开、可复制的身份；不能只用共同的 revision 字符串（如所有版本都叫 content-v2）和 hash 让用户认版本。业务定义、模型／运行环境、展示变化分别说明，不把声明补充描绘成所有业务节点均换了方法。

### 方法定义与运行实例

下表是六项生命周期任务可调用的四种**图语义**，不是侧栏中取代生命周期入口的四个标签。方法与单次执行共享完整流程布局，运营观察沿同版流程聚合实际记录，演进切换为版本关系图。任务可在需要时切换图语义，各视图通过准确身份联动，不混用边的语义：

| 模式 | 图里表达什么 | 点节点看到什么 |
| --- | --- | --- |
| 方法定义 | 准确版本的节点、允许路径、并行、条件、返工与端口类型；不需有 run | 已冻结的目的、执行器、模型／推理档、工具、输入输出；有记录的完整 Prompt 与 schema 按需展开 |
| 执行过程 | 某个准确 Case/run 的实际实例、状态、路径、业务轮次和产物 | 本次有效配置、输入资产、产物、对应意见、失败／重试和可观测会话 |
| 运营观察 | 某个版本在指定时间窗／案例集合中的覆盖、阶段产物与运行情况；并非一次实际执行 | 该节点的相关资产集合、各项评价及覆盖、典型失败／反例，继续下钻准确 run |
| 版本演进 | 节点是方法版本，边是明确前驱与变更关系 | 此版解决的问题、设计／变更理由、受影响节点、验证结果与采用；点击版本回到方法全图 |

方法模式下端口是**预期类型**；执行模式下产物是**实际保存的准确版本**。没有生产成功时不显示产物卡。控制边与资产数据边分层：默认突出流程，选中节点或产物时才显示相关输入输出连线，避免整张图被引用线覆盖。

定义中的循环保持全局可见；执行中同一节点可有多次业务实例。节点可显示“执行 3 轮”，用户选择第 2 轮查看第 2 稿及准确意见。技术 retry 属于该实例，不冒充下一业务轮；存在失败后成功时同时保留最终状态和曾有失败的标识。布局不能用最后创建时间推断执行因果。

运行状态只覆盖该 run。历史推导、原始明确记录、未知／未映射分别标注；未选过的允许路径不画成真实执行。没有当时流程快照的历史，提供标明来源的兼容说明，不回写历史指纹。节点类型用颜色与文字，运行状态用边框／图标与文字，不让一种颜色同时代表执行器和成败。

历史版本没有保存 nodeDefinitions 或完整 Prompt 时显示“当时未记录”；实际 context 中有内容时可作为本次执行证据另读。不能从当前工厂或同名角色补写成历史版本的冻结定义，也不能把某次实际配置冒充全部历史运行共用的声明。

### 运营观察与关键阶段资产集合

用户可以从“V2 最近七天”或明确 Case 集合进入运营观察。顶栏保留所选版本、时间／时区、纳入范围和证据截至时间；显示全部请求／运行、失败及无产物、评价覆盖和人工介入。图中节点显示有记录的执行次数与产物／评价摘要；部分记录未知就标未知，不能把多个 run 拼成一条虚构的实际路径。

点研究／作者等关键节点，打开**该节点在所选范围内的资产集合**，而不是自动取最新一次 run。比如：选 V2 → 最近七天 → 研究节点 → 本期各案例的研究结果 → 筛看有明确好评、发现问题或尚未评价的资产 → 并看两份 → 跳回准确运行、输入与会话。首期支持明确范围与维度，个性化默认排序根据实际使用再校准。

集合卡片至少包含业务名称、生产版本／Case／run／轮次、关键评价维度、判者与标准、评价状态和时间。默认按时间或明确选择的维度排列；“最好”须说明按谁、哪版标准、什么维度和多大样本判断。未评价不等于差，喜好不同不合并成同一排名。选择对照对象保留完整来源，不能出现“资产 1”式无上下文标签。

不同方法的“研究阶段”即使同名，也不能直接合并：跨版本对照需明确节点／业务角色映射与 schema、标准兼容性；节点拆分或合并时显示变化。先支持准确版本内的集合浏览，再按明确映射做跨版本比较。

复盘保存本期观察范围、代表案例与反例、重复问题、判断及下一步，可由人或认知 Agent 完成。它是“继续使用／限制范围／回退／开启新候选”的决策记录，不要求每次都改方法。观察可以先由已有事实查询和人工记录支持，自动评分、指标看板与定时复盘并非本轮已实现。

### 案例与一次运行

Case 是具体业务题目，可被多个方法版本反复处理。案例列表与版本列表是同一组事实的两个入口：从版本看它处理过哪些案例，从案例看哪些方法跑过它。提供 Case × 方法版本的运行摘要，点格子可看全部尝试；空格表示无运行，失败、未评价和质量未知分别显示。

案例、版本和 run 不互相替代。Case 的输入可有多份冻结 manifest，对照页必须显示输入是否相同。run 列表显示业务名称、方法名称、时间、状态与产物摘要，不能只有“第 1 次、第 2 次”。历史作品、本次输出和已接受作品分别保留；最新一次额度失败不能把以前已保存的稿件从 Space 的最近产物入口隐藏。

manifest 身份只证明其冻结范围内的资产绑定，不单独证明全部实验条件相同。比较同时核对 Case 身份及约束、manifest、运行有效配置、标准和判者；字段实际位于哪里就从对应冻结记录读取，不把所有条件宣称成一个 manifest hash 已覆盖。

选择一个 run 时，由其真实绑定同步切换准确方法版本。切换方法版本时，若当前 run 不属于它，退出执行叠加并清楚显示“此版本尚无所选案例的运行”，不静默嫁接另一版状态。计划中的未启动条目显示为“计划”，不能算已跑案例。

创建运行从选中的准确版本或 Case 出发，复用明确选中的输入快照，展示执行条件和动作影响。只读导航不能启动模型。失败页优先说明停在哪、实际已有何物和下一步可用动作；无产物时不提示“过程稿仍可阅读”，也不让用户重新填写全部材料才能知道发生了什么。

业务工作台需要覆盖发起到交付，不只是 run 列表：

1. **发起。** 写下业务要求与验收标准，挑选已有材料或导入；显示缺失项和可执行的方法版本。启动前明确本次输入、约束、模型、工具与已知限制；需要运行才显式提交，普通准备工作可保存。材料补齐不自动派发。
2. **跟进。** 列表区分准备中、执行中、需要处理、已有候选和已确认结果，状态必须有事实依据。一个 Case 的某次失败不覆盖其他运行结果；待办跳到准确 run／节点／产物，说明为什么需要处理和有哪些可用动作。没有持久人工等待机制时不能画出虚假的“待审批”状态。
3. **协作。** 人或 Agent 补材料、反馈或手动修订都留下身份和准确目标。已完成 run 的内容不被覆盖；补充后的后续执行明确绑定新的输入或执行实例。重试、续作、新运行分别说明实际行为，不承诺当前执行器不具备的恢复能力。
4. **审阅与交付。** 查看本次候选与历史结果、对应意见及尚未解决的事项。用户接受作品是独立、明确的决定；交付指定准确资产版本，保留何时以什么形式交付的记录。复制／下载能力与外部发布能力分别标注；新稿不自动替换已交付版本。
5. **反馈。** 反馈绑定实际交付物与 Case，可进入本次修订或方法改进。意见“已经收到”和问题“已经解决并复核”分开；尚无复核证据就保留未验证状态。

接受、导出和交付分别留痕。点击复制／下载只证明一次导出动作，不能自动标记“已交付”。交付须有独立持久记录，至少绑定 Case、准确资产版本、交付方式、时间、操作者及可用回执；没有外部回执时标明是人工登记，尚未交付则显示“准备交付”。外部收件方、链接等信息按权限保存。当前缺少这类记录或接口时，要作为实施缺口建设，不能借用资产接受状态冒充。

CONTENT 的具体目标路径是：建立一个选题 → 选资料并说明受众／内容要求 → 选择已部署 CONTENT 方法 → 显式运行 → 从图上看研究、三轮写稿与审阅 → 选定准确稿件、评价并交付 → 收集反馈。B3 成片与公开发布属于后续流程，不因为有了“交付”按钮就宣称已接通。

### 资产阅读

图上点击某轮输出，右侧打开资产阅读区；默认阅读业务内容。顶部紧凑保留 Space、Case、方法、run、节点／轮次与资产身份，支持展开全宽阅读并返回原图位置。关闭或浏览器后退恢复选择和缩放，不回到另一次运行或列表首页。

阅读区分为内容、关系、评价、执行证据。关系可以按需与正文并看：依据什么生成、修订自哪份稿、谁使用了它、哪些意见评价这一版。点击关系切换准确资产，并保留返回当前对象的路径；来源定位到准确父资产内的片段，不能跳到最新材料库中一个同名来源。

审阅稿件时直接提供该稿对应的冷读、核查与主编意见及前稿并看入口，不要求先找“哪个下游节点使用它”，再去那个节点找意见。内部审阅资产与独立四问分开显示；有无评价、是否建议修订、用户是否接受和本 run 是否最终输出分别说明。对不同稿件的相似意见，只能标注可查的对应关系，不能用文本相似度擅自宣布某个问题已解决。

同一研究被三轮复用，显示一份研究和三轮使用关系。三稿分别标业务轮次，即使数据库中各自都是 logical asset 的 version 1。稿件意见按准确被评对象匹配，不取 run 的最后一份审阅。正文、逐段画面、证据和原始 JSON 分层，不把它们全部串成万像素长页。

资产库是检索与跨运行比较入口：按类型、Case、方法、run、节点／轮次筛选，摘要包含业务名称与生产来源。比较选择器使用这些摘要，不能要求选择“资产 1”。选中资产可定位生产节点或在当前上下文阅读。未知类型采用带字段名称的结构化回退；业务 reader 输出可序列化阅读结构，不能运行资产正文中的任意脚本。

### 资产工作台的完整职责

资产工作台以内容为中心，提供可筛选列表／业务适配的卡片、阅读区和版本／关系区。文本、结构化研究、图像、视频与附件采用合适的阅读器，媒体能力按实际支持情况开放；不能全部退回 JSON，也不能用空播放器暗示已有媒体服务。

| 生命周期 | 用户必须看清与能控制的事项 |
| --- | --- |
| 导入或生产 | 所属 Space、schema／类型、原始来源、提供者、校验情况；人工上传与节点生产分别标注；未被 run 使用的材料也可查到 |
| 阅读和组织 | 业务角色、可读名称、Case／run／轮次、内容摘要；按资料、产物、意见等业务分类组织，不能只有底层类型名 |
| 版本与修订 | 逻辑资产与准确版本分开；修订保存新版本，保留原文和差异；人工修订标明来源，不能冒充 Agent 当轮产物 |
| 关系与影响 | 由什么生成、引用／修订／评价什么、被哪些节点和运行使用；关系类型可区分，精确到已有片段引用；图上的流程边和资产关系不是同一种边 |
| 复用 | 选准确版本加入新的输入清单；检查目标 schema 和访问范围；材料升级不改写历史 manifest，也不静默替换正在运行的输入 |
| 对照和处置 | 并看准确版本、按业务字段比较；区分候选、被接受与实际交付；归档／删除需说明引用影响，不提供无提示的关联历史破坏 |

对大文件，产品需要正文预览、下载、对象是否可用、来源与引用保持稳定。元数据／版本关系由 Space 管理，对象存储承担大文件；具体部署与成本另见存储方案，本轮不能把本地临时路径当成已建成的持久云存储。批量治理、跨 Space 共享、保留策略和大媒体服务可后续实现，但不从设计中消失。

### 方法迭代与比较

方法迭代在工作流的演进视图中，用 Archify 版本图呈现明确前驱关系。这里的节点是方法版本，边是版本演进，不能混入节点执行流。时间顺序不证明继承，没有前驱的版本显示独立节点，不补造因果边。

选择一个版本或版本变化，可见改动原因、配置差异、相关问题／假设、验证计划、各 Case 的配对结果及采用决定。版本血缘、实验、评价和采用是不同证据：没有独立 iteration 记录，仍应能查看已存在的版本图和验证计划；不能以一张表为空就把整个方法演进页面显示为空。

迭代图的主要阅读链是：**原问题和观察证据 → 原因假设 → 改了哪些节点／资产交接 → 怎样验证 → 改善、退化及未解决项 → 采用与后续使用效果**。箭头本身不证明因果。没有证明时区分“想解决”“本次观察到改善”“仍未验证”；没有前驱的首版也能看到业务目的与设计理由。已采用版本与候选分支并列可见，查看或发布候选不会改变生产采用指针。

比较有三个明确对象：同一 run 内的稿件、两次 run 的结果、两个方法版本及其验证集合。条件差异先展示，再阅读产物和四问。基线与候选在准确输入、标准、判者和模型上的差异不能隐藏。局部改进不推导成跨案例成熟；失败或没有评价时保留未知，不记零分，也不虚构采用。

评价不是另一个只能在列表里填写的页面。图上或资产工作台都能对当前准确对象记录四问；工作流内的运营观察／演进视图聚合这些意见，按需提供审阅队列，回答哪些问题反复出现、下一轮为什么改、哪些改善有证据、哪些仍未解决。结构化问题追踪尚未接入时，只呈现已有问题与结论，不依据一次主编 pass 自动把历史问题批量关闭。

### Agent 配置、会话与长期知识

| 信息 | 归属与使用方式 |
| --- | --- |
| Agent 的角色、Prompt、模型、工具、读写合同 | 方法定义中的节点；从图上检查。修改在草稿／新的方法版本中发生，历史定义保持不变；首期可由 Agent + CLI 修改并发布，不要求先实现通用拖拽编排器 |
| 本次实际配置、输入上下文、可获取的会话与工具事件 | 准确 run／节点实例；从结果或异常点开。提供声明与实际证据的差别，模型额度失败时不假造返回值或费用 |
| 对业务有复用价值的经验、标准与认知结论 | Space 的有来源资产／记录，带版本、适用范围与证据。经选择装配到后续节点，不能将全部历史自动灌入每次上下文 |
| 凭证、连接、权限、限额、保留政策 | Space／宿主配置辅助入口；只展示授权者需要的状态，配置快照与操作日志不泄露密钥 |

记录 session 解决“发生过什么”，提炼知识解决“下次应该使用什么”。长期保存不等于每个节点都有权读取，也不等于全文进入 Prompt。外层认知／执行聊天尚未自动同步时显示覆盖范围；近期先保存重要决定、证据引用和验收结论，不声称已有完整自动知识体系。

## 上下文与状态合同

1. 页面和深链接保存 Space、工作流、生命周期二级项、方法版本、Case、run、图视图及可选的节点实例、轮次、资产选择。刷新、后退、分享链接能恢复相同任务与对象；指向二级项的深链接自动展开对应工作流标题，折叠只改变导航显示；API 校验这些身份的真实关系。
2. 方法定义、当前有效执行配置、实际提供者事件分别呈现。SDK 分类与具体 runner 名称同时可见；SIWC Responses 不能被写成官方 Agents SDK。
3. 执行状态、产物角色、评价结论、用户接受、方法采用分开。主编 pass 不代表用户接受，发布方法不代表采用。
4. 加载、空数据、权限不足、记录缺失、服务失败、数据过期分别可辨认。读取错误不能显示“暂无记录”；部分加载失败时保留已读正文和重试入口。
5. 活跃运行增量更新状态、事件和产物；刷新不丢选中节点、草稿评价或阅读位置。执行完成后能查到停止原因，不能只依赖 toast。
6. 首屏图需能读到主路径和标签；搜索定位节点，聚焦后能返回全图。支持键盘选择和等价文字路径。手机将详情转成阅读层，关闭后回原图；不把三列直接缩小塞进窄屏。

## 展示契约需要描述什么

展示定义独立于业务正文及执行状态，绑定准确 workflow 版本、entrypoint 和 schema 版本。它声明业务用语、主产物／支持材料／审阅角色、阅读结构、比较字段及已注册动作。拓扑来自 ProcessContract，实际关系来自授权查询，不允许展示声明编造 SQL、脚本、执行边或任意 URL。

业务接入还需声明发起表单的字段与约束、可选输入资产的类型、结果槽位和支持的操作。CONTENT 可将 Case 命名为选题，把口播稿和研究材料用不同阅读器展示；另一业务复用相同外壳而替换这些语义。表单校验依据 schema，动作依据服务端能力与权限；展示配置不提供任意代码执行，也不能用字段是否可见替代授权。

现有 WorkflowPresentation、BusinessPresentationAdapter 与服务端 AssetReader 可复用。当前 reader 输出 title/sections 等可序列化内容，由页面 renderer 呈现；新前端可先消费这种结果，再按需要增加媒体／段落块，不以重写全部业务阅读器作为第一步的门槛。具体已有类型和导出见[Space 接入](space-storage.md)。

注册时校验完整 schema 引用、字段路径、组件类型、结果槽位和动作能力。复杂类型需已部署的 reader；不支持时明确回退，不静默套用别的业务视图。阅读视图不能修改不可变历史正文。

### 真实关系来自服务

前端消费面向页面、经过授权和分页的读模型，不下载整个 Space 后自行拼关系。优先复用现有 manifest、run、context、dependencies、生产收据、review、comparison、predecessor 与 adoption；缺少的语义再补合同，不能先建第二套资产数据库。

当前多数事实与进程内查询已具备，稳定 Space JSON HTTP API、增量事件契约及新的统一应用仍需实现。字段名和端点由技术方案定义，页面草图不能冒充 API 已存在。流程、实例和资产关系的技术边界见[流程与资产合同](workflow-process-assets.md)。

## 版本与权限边界

方法版本、资产正文版本、展示版本与采用指针分别保存。单纯排版更改应独立绑定展示，不要求重新跑模型；影响声明或执行实现的变化继续遵守不可变方法和部署校验。比较页须解释变化层级，不能为了视觉清晰抹去真实指纹差异。

服务端检查 Space 权限、准确对象和动作状态，浏览器不能直接访问数据库、任意文件或提供者凭证。折叠不是权限控制。评价、接受作品、采用方法、运行和取消是不同动作；提交返回准确对象的持久回执。图里的按钮不隐式扩大执行范围。

## 首轮实现分工与验收

本节替代此前“页面分别可用即可通过”的整体验收方式。认知侧负责产品定义、真实路径体验和完成判断；执行侧负责技术方案、共享实现与集成。每次交付明确标为设计、交互原型、接入实现或产品验收，不把可点击 mock 称为真实业务工作台。

第一批应交付一个连贯的纵向路径：Space → 准确方法全图 → 已有 Case/run → 具体轮次节点 → 可读资产 → 返回图。随后以同一对象模型接入版本比较与迭代图，不继续发布彼此孤立的后台页。先使用已有真实 MiMo 数据与失败记录，不新增创作模型调用或伪造评价。

这批只验收**只读贯通路径**，不能因此宣布整体工作台完成。后续批次补日常发起、执行协作、资产导入／版本／复用、结果评价与交付，再贯通方法验证和采用。首期产品的最低要求是这两个闭环都可完成；具体先后和现有能力复用写在实施计划，不要求一批同时造完。通用可视化流程编辑、多用户任务分派、复杂通知、外部发布、B3、多 workflow、跨 Space 与大媒体治理后置。

| 必须亲自完成的任务 | 通过条件 |
| --- | --- |
| 从 Space 找方法 | 无运行也能看到全图，能说明所看版本与采用版本的区别 |
| 分辨多个版本 | 不读 hash 也能知道各版为何产生、哪些仅环境变化、是否可执行 |
| 找这一版的例子 | 从版本找到准确 Case/run；从 Case 返回其方法，版本绑定不丢失 |
| 看 MiMo 三稿 | 在同一 run 中选择三轮作者产物，并确认研究只生产一次被复用 |
| 从第 2 稿追依据 | 能定位作者第 2 轮、上一稿、研究、反馈与准确对应审阅，并回到原图 |
| 阅读长资产 | 不滚过整篇稿件才能找到流程；正文、画面、关系与证据可切换 |
| 查看额度失败 | 研究节点失败、后续无执行证据、无稿件；历史旧稿仍可发现 |
| 查版本证据 | 第一批从版本详情可到已有前驱、计划与准确运行；独立版本图和跨版本比较在后续集成验收，不能误报已有计划为空 |
| 刷新、后退和深链接 | 同一个版本/run/节点/资产可恢复，不静默切到最新对象 |
| 识别完成边界 | 不因原型有样例、测试通过、图显示成功或主编 pass 就宣称产品完成或业务有效 |

完整首期产品还须独立验收以下实际任务；当前只读原型不计通过：

| 必须完成的业务任务 | 通过条件 |
| --- | --- |
| 发起新选题 | 从业务要求、已有／新导入材料到准确输入与可执行方法；显式派发，返回持久回执，不通过导航启动 |
| 处理运行中断 | 看见真实原因与已有结果；只提供支持的取消、续作或新运行，效果和对象清楚，历史保留 |
| 复用与修订材料 | 能选定准确版本用于下一次 Case；创建新版本不改变旧 run／manifest 的材料 |
| 评价与交付稿件 | 对准确稿件留四问、看对应审阅，明确接受和交付版本；不能用主编判断替代人接受 |
| 根据反馈改方法 | 从具体问题与证据形成修改，发布新版本，验证后比较；有依据地决定采用，未解决项不被清空 |
| 看完整方法演进 | 版本图、验证集合、比较、失败和未启动关联可读；没有 iteration 行也能呈现已明确记录的版本前驱和计划 |
| 理解第一版为何这样设计 | 无 run、无前驱时也能从业务目的到关键节点理由；缺失历史意图如实标明 |
| 看关键阶段的近期资产 | 在准确版本与时间范围内，从节点找到多 Case 的资产与评价，选两份比较并回到来源；不以最新一份代替整个集合 |
| 一段时间后集中复盘 | 可恢复纳入范围、失败／未评、人工负担与典型样本，明确继续使用或新改动；真实一周数据不存在时不能拿合成时间戳声称通过 |
| 接手或停用方法 | 恢复目标、采用版本、最近复盘与未解问题；清楚区分历史可读和新运行可执行 |

认知侧须先独立完成上述真实任务，明确通过项、失败项和剩余缺口，不能把整体判断重新推回用户来做。用户后续反馈是校正产品的依据，不能用局部通过项覆盖其不满足，也不能将用户未回复视为接受。具体发现见[认知实用审查](cognition-execution-loop.md)，进度仅在[建设状态](harness-roadmap.md)维护。
