# 存储架构：身份、字节与提交一致性

存储要支持的不只是“文件保存成功”，还包括：下次能读到同一份材料，能解释谁用它生产了什么，失败后知道哪些结果可以复用，以及方法变化后仍能读懂旧工作。因此系统把**业务与执行事实放在 PostgreSQL，把附件字节放在 BlobStore**，通过准确资产版本连接二者。本地工作目录只负责本次执行。

本页解释当前共享存储的结构、提交与故障边界。节点装配见[执行 harness](postgres-sdk-plan.md)，资产访问合同见[Workflow Space](workflow-spaces.md)，调用与部署例见[Space 接入](space-storage.md)。它覆盖 shared harness 与 creation 接入路径；research、analysis 保留各自工作台和适配，既有报告、数据库与媒体没有自动迁移。

## 三种责任为什么分开

| 存储责任 | 保存内容 | 为什么这样分工 |
| --- | --- | --- |
| PostgreSQL 业务领域 `ws_*` | Space、schema、方法版本、Case、InputManifest、资产正文与版本、依赖、附件清单、context/session、评价和采用 | 版本与关系需要约束、授权、并发检查及共同提交，不能靠文件夹名称和对象标签推断 |
| PostgreSQL 执行账本 `aw_*` | Run、step、attempt、事件、原生 artifact、步骤提交收据 | 执行事实与业务事实职责不同，但必须通过准确身份关联；原生 artifact 可以显式映射到 Space AssetVersion |
| BlobStore | 附件的真实字节；当前新字节可写私有 R2，旧字节保留在 PG | 字节存储与业务关系的变化速度、大小和提交边界不同；对象 key 不承担方法、评价或资产状态语义 |

`aw_*` 与 `ws_*` 可以在同一个 PG 数据库中，领域服务将需要共同提交的记录放进同一事务。两组表不是两个互相竞争的正本。普通结构化资产正文和已采集的 session 事件目前仍在 PG；R2 接入没有把所有正文与 trace 自动迁到对象存储。

本地下载、工具工程和缓存属于可再生成的读出物。只有本机路径、可访问 URL 或文件 hash，尚不能证明原件已经持久入库。宿主加载数据库与 R2 配置，节点和浏览器接收受限内容，不接收提供者凭据。

[打开可交互架构图](../../../docs/diagrams/storage-harness-20261010/storage-harness.html)

领域服务接收一个 `BlobStore` 端口。配置 R2 时，`RoutedBlobStore` 将新字节写到 R2，依据历史清单中的 key 把旧 PG 附件送回 `PostgresBlobStore` 读取。**配置新后端不会修改已有清单、资产版本或 Run。** 同一 Space 已登记相同 hash 的内容，先核对并复用已有清单，避免重新上传时悄悄改变其后端。

R2 当前使用私有桶、S3 接口与内容键；浏览器读附件经过同源授权 API，不直接拿桶凭据或以公开对象地址读取。API 从准确资产版本取附件列表，先确认 blob 与该版本绑定，再读取字节；服务端与客户端分别校验完整性。缺少 R2 配置时读取 R2 key 会明确失败，不回落到临时本地文件。

## 从逻辑资产到一份准确内容

| 身份 | 负责什么 | 会怎样变化 |
| --- | --- | --- |
| `assetId` | 同一逻辑资料或作品的稳定身份 | 可以追加版本，当前 head 只是指针 |
| `assetVersionId` | 一份不可变正文、schema、来源、依赖和附件清单 | 不被后续改稿覆盖；Run 与评价引用它 |
| `payloadHash` | 校验结构化正文的内容 | 对应准确正文，不替代版本来源和授权 |
| `BlobManifest` | Space 内附件的 hash、size、mediaType 与后端 key | 当前附件 ID 为 SHA-256，在同一 Space 内核对并复用 |
| 对象 key | 按后端读取相同真实字节 | 当前新 key 含 Space 与 SHA-256；不以文件名或临时 URL 作业务身份 |
| `InputManifest` | Case 的输入槽到准确资产版本的绑定 | 创建后不跟随资产 head；新材料需显式用于下一次 Run |

例如，一份“材料包”追加了新版，并不改变此前研究节点收到的材料版本。两份稿件可引用同一个素材字节，却具有不同的正文、来源和依赖。SHA-256 证明字节一致，不能证明材料真实、授权充分、内容质量合格或两个版本有相同业务用途。

原始模型响应也不自动成为资产。它可以作为 session 证据保存；只有通过输出合同并提交准确版本，才具备可供下游绑定的产物身份。人工修订保留自己的来源，不用修改模型原响应来制造“原方法已成功”的历史。

## 上传、资产绑定与 Workflow 配合

![文件到 Workflow 的配合图](../../../docs/diagrams/storage-harness-20261010/workflow-storage.svg)

[打开可交互配合图](../../../docs/diagrams/storage-harness-20261010/workflow-storage.html)

| 步骤 | 执行与记录 | 这时能保证什么 |
| --- | --- | --- |
| 1. 上传字节 | 宿主认证 Space 写权限；计算 hash；按内容 key 条件 PUT，GET 读回并核对大小和 hash | 对象确实保存了这份字节；尚未说明它属于哪份业务资产 |
| 2. 登记清单 | 校验成功后写 PG BlobManifest；同 Space 同 hash 已有清单先验证并复用 | 得到可核查的附件身份；清单仍可尚未被任何资产引用 |
| 3. 导入或发布资产 | schema 校验正文；核对依赖和附件实际字节；以来源与预期 head 创建新 AssetVersion | 正文、来源、准确依赖、附件引用一起入 PG，不以“上传成功”代替资产提交 |
| 4. 冻结本次输入 | InputManifest 绑定准确资产版本，Run 绑定方法版本、入口、Case 与清单 | 上游出现新版本不改写本次执行依据 |
| 5. 节点交接 | context 保存实际读取版本、字段投影和交付内容；节点提交准确输出与依赖 | 可追生产与消费；共享节点客户端不获得任意 Space 读取能力 |
| 6. 读取与判断 | 下游、工作台、CLI 按准确版本读正文和附件；评价、接受、采用另行记录 | 文件下载或节点成功不会自动成为接受、交付或采用 |

上传时同时限制空内容、单对象大小和媒体类型。写入属于当前宿主明确启用的能力；HTTP 还要复核主体、成员身份、Origin 与 CSRF。当前受控写入入口是宿主服务／CLI，浏览器侧负责附件阅读与下载。

## PG 内部的共同提交

资产追加对逻辑 head 检查 `expectedHead`，避免两次并发修订无声覆盖。schema 引用和正文 hash 随版本保存；准确依赖、附件引用、生产来源不依靠随后扫描文件重建。节点 `submitNode` 还检查输出槽、必需依赖和执行主体。

在 Space runtime 发布路径中，资产版本、依赖、输出绑定、相关会话事件及 core 步骤完成收据可以使用同一 PG 事务。若事务没有完成，不应出现“步骤成功但正式产物不存在”的半份提交；原始模型回答仍可能在更早的独立记录中保存，必须与正式发布区分。

持久幂等键处理重复请求：同键同内容返回原收据，同键内容变化会冲突。幂等不是允许重跑模型的通行证；先按原身份核对已保存响应、步骤和提交结果，再决定是否需要新尝试。

## 跨存储失败怎样判定

**R2 PUT 与 PG 事务没有共同回滚。** 当前协议先保存并校验字节，再登记和绑定。它能对账相同内容，但不意味着每个外部阶段都有完整的持久状态机。

| 失败位置 | 当前读取或重试行为 | 保留的限制 |
| --- | --- | --- |
| R2 写入失败，清单还没登记 | 上传失败；不生成可用清单或资产 | 已失败请求需按原内容重试，不能只补一条“文件可用”元数据 |
| R2 写成，但 PG 清单登记失败 | 同 Space／hash／mediaType 重试；条件 PUT 不覆盖，校验后登记清单 | 可能留下未引用对象；没有自动上传意图协调器或孤儿清理器 |
| 清单存在，但资产提交失败 | 复用已验证清单，按原资产提交键对账 | 清单存在不等于已有业务产物或 Run 输入 |
| PG 事务成功，调用者没有收到回执 | 读取持久幂等收据和准确版本 | 换键重新提交会被当成新工作，不是正确的未知结果处理 |
| 对象缺失、内容或大小不符 | 明确不可用／完整性错误；拒绝附件读取或资产提交 | 无自动备份修复；不可拿本地同名文件冒充原件 |
| 请求的 blob 未绑定所选资产版本 | 拒绝读取，即使同 Space 有这个 blob | 合法 blob ID 不足以证明这次阅读关系合法 |
| 历史 PG blob 与新 R2 内容并存 | 清单决定读哪一后端；同 hash 已有清单优先验证复用 | 没有自动迁移、跨桶寻址或“哪个能读就用哪个”的回落 |
| 宿主或本地源文件被移除 | 已入库内容按 PG 清单与配置后的 provider 读取 | 临时文件可删，长期 PG/R2 数据及部署配置仍是必需条件 |

模型和第三方工具还有另一条边界：它们的副作用不受 PG 或 R2 幂等保护。收到取消或网络错误不证明远端没有执行。这部分恢复由[执行 harness](postgres-sdk-plan.md#4-replayresume未知结果与租约)说明，不能用存储事务代替。

## 保留、清理与生产能力还缺什么

已有资产可能被多个 Run、修订、评价或采用记录引用。删除对象前必须考虑这些引用，而不能按“执行结束”或“最后访问时间很早”判断内容无用。当前没有自动对象 GC，也没有声明数据库和对象桶可以独立随意回收。

完整生产设计还需围绕具体业务作出并验证以下决定：

| 需要的决定 | 为什么影响正确性 | 当前边界 |
| --- | --- | --- |
| 大文件上传、分块／断点与校验协议 | 中断后哪些字节可复用，何时能发布可读资产 | 当前单对象 ≤16 MiB；没有 multipart／断点协议 |
| 保留、归档与删除规则 | 删除会不会破坏历史 Run、评价和来源 | 尚无通用引用清理、生命周期策略及删除对账 |
| PG 与对象字节的备份恢复 | 恢复点是否同时包含可读正文、引用和字节 | 尚无生产备份手册、恢复目标或灾难演练证据 |
| 扩容、区域与成本边界 | 字节量、调用次数和媒体使用模式不同 | 尚未由完整制作业务验证容量与治理参数 |
| 多用户与执行器隔离 | 服务角色检查之外是否仍有数据库或工具旁路 | 没有数据库 RLS、操作系统级隔离或生产多租户证明 |

这些是需要后续任务闭合的架构决定，不是因已配置 R2 就自然成立的能力。CONTENT 与完整媒体制作的业务验收也分开判断。

## 实现、接入与证据

共享的[BlobStore 实现](../packages/spaces/blob-store.ts)包含 R2 内容键、条件写入、读回校验和旧 PG 路由；[Space 服务](../packages/spaces/service.ts)负责清单、资产和授权；[HTTP 控制器](../packages/space-api/server.ts)负责准确版本附件读取。creation 仅装配宿主配置，没有复制一套存储服务。

宿主可以通过私有文件配置 R2，旧进程需按此配置重新启动才会启用新后端。配置、CLI 上传／导入／下载用法和基本组装放在[Space 接入指南](space-storage.md)，架构页不重复维护密钥字段与命令手册。

2026-10-10 的非业务隔离样例验证了真实 R2 写入、重复写入及新客户端读回；CLI 在独立 Space 上传并绑定准确版本，重建宿主、删除本地源文件后再次下载，70 字节与 SHA-256 一致，PG 字节表没有该 R2 对象。确定性故障测试另覆盖对象写成但 PG 记账失败的重试、旧附件读取和篡改拒绝。前端字节校验已有组件测试；独立普通工作台实用验收与整体产品阶段另见[建设路线](harness-roadmap.md)。
