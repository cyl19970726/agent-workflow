# Agent Workflow 的建设顺序与当前状态

目标由[产品需求](product.md)定义，交互以[Space 工作台产品定义](workbench-presentation.md)为准，模块关系见[架构](architecture.md)。本页是唯一的当前实现状态与下一步入口，包含 2026-10-07 真实使用与配对验证、2026-10-08 的版本认知路径核验，以及 2026-10-09 文档重构后的下一阶段建议。日期化实施记录保留当时的范围与证据，不作为完整产品已交付的声明。

**当前结论：存储、执行、图和评价已有可复用能力，整体前端产品未通过验收。** 用户明确要求工作流工作台以完整流程图为主工作区，相关信息点击后原地展开；同时由业务和资产工作台支持实际工作，评价就近发生，运营观察与演进留在工作流中。认知侧实用审查发现入口割裂、部分展示与记录不一致，且从业务发起到交付、资产管理与复用的整体使用尚未贯通，不能将其缩写为“导航略可改善”。

推进方式见[认知驱动的执行循环](cognition-execution-loop.md)：认知 Agent 持续维护目标、实际使用、诊断与排序；执行 session 完成明确批次并回报；认知侧独立验收，再决定下一步。不能把执行摘要当作已经满足用户需求。

**批次 A 已通过真实只读路径验收。** 在产品、技术方案和原型复核之后，共享 React 工作台及 HTTP 读接口已接入 PostgreSQL，creation 提供同源宿主。认知侧实际检查了 MiMo 第二稿、前稿并读、同一研究、对应三类意见、准确轮次返回、版本切换和资产目录；移动阅读证据及 54 张历史表前后摘要也已核对。首次及部分后续读取仍约 3–5 秒，历史未保存的定义保持缺失。它没有发起新模型运行或写入评价／采用，完整产品和手机全生命周期尚未验收。后续最小批次 B 的准确业务动作、运行跟进及已有评价／验证读回，已按[前端实施计划](space-frontend-implementation-plan.md)继续完成下述限定复验；每次真实模型调用仍须先核对当前部署和冻结条件。

**有界内容对照和修复后的单案例实用路径已完成独立复验。** 认知侧从新界面发起同条件 MiMo 基线与候选，两边各三稿后未收敛，准确终稿的独立 Agent A 四问、比较、问题、处理决定和 iteration 均已落入 PostgreSQL。机制解释有局部改善，表达负担仍重，不能宣布作品合格或方法已采用。额度条件已由这两条真实运行核验；此前额度和工具契约失败保留。默认图、就近详情、状态、评价身份、跨运行双稿和版本迭代入口已修复并实际走通，手机阅读及返回也已检查。计划列表部分首读仍约3.4秒；旧实验版本因新部署指纹当前不可再次执行，下一次新运行须登记准确部署。范围与未完成项见[前端实施计划](space-frontend-implementation-plan.md)，内容结论见[认知记录](cognition-execution-loop.md#修复后的真实执行与配对2026-10-07)。

## 下一步按什么顺序推进

### 2026-10-09：下一阶段建议——共同理解一版方法，再完成有依据的迭代

**当前阶段：先完成 Space 业务理解 → 首版设计 → 准确版本的上下文。** 用户已确认整体建设方向；上一批交付了目标／版本信息展示、预期资产图和只读 CLI，并完成工程与部分只读检查。随后用户指出看不到清晰业务目标及 workflow 设计思考。本次独立打开现行页面也确认：业务目的仍是一句用途，问题约束与成功标准为缺失提示；版本动机主要是部署登记说明。故不能把业务目标与首版设计这一阶段记为完成，当前继续补齐这条起点路径，后续再随生命周期逐段构造和使用产品。

规划时已核对文档与相关源码；本次进一步只读查看业务目标与准确版本页面，没有重新运行 workflow。共享发布、验证计划、比较、问题、iteration、采用服务，以及刚交付的图和 CLI 能力继续复用。已有普通业务与有界方法对照也不重记为待从零建设。当前缺的是把业务理解真正形成、保存并用于设计首版的工作路径，仅把已有字段展示出来没有完成这项任务。

#### 为什么先做这一段

上一版规划从“读全一个已有版本及其执行证据”组织任务，偏重后半段的理解与追溯；当前应先补“业务目标怎样被理解，并推导成首版方案”的起点。否则用户看见版本、配置和方法图，仍不知道这些设计为什么成立。按生命周期逐段构造，每段都形成可实际使用、可保存和接续的结果；阶段使用暴露的问题再修正本阶段或前一阶段，不要求一次建完全部页面，也不要求先把业务研究到没有未知。

共享 `inspectSpace` 及上一批新增的只读 Operator CLI 可以查询已有目标、准确版本、节点和预期资产；完整 Codex attempt 细节还可能位于私有本地 trace。消费方已有设计预览、发布和验证命令可供参考，但“形成／修订业务理解 → 保存首版设计 → 关联准确方法”仍需贯通。优先复用已有文档或资产版本和服务，只补当前任务必需的保存、读取、关联及交接，不建设庞大的 Agent 管理框架。发布使用宿主提供的方法工厂，采用服务当前要求经过认证的人类主体。

实现依据：[操作者查询](../packages/spaces/operator.ts)、[方法宿主](../packages/spaces/method-workbench.ts)、[验证工作台](../packages/spaces/validation-workbench.ts)、[共享服务](../packages/spaces/service.ts)，以及旧版 Codex trace 实现 `packages/codex/src/trace.ts`（历史实现已移除）。

#### 三个里程碑及通过条件

| 里程碑 | 具体交付 | 通过条件 |
| --- | --- | --- |
| 1. 形成可接续的业务理解与准确首版 | 在 Space 中形成并保存业务问题、目标、关键业务步骤、设计想法与未知；据此说明首版执行目标、设计理由、预期资产和取舍，关联当时业务理解，再形成准确版本。现有 Archify 和 CLI 承接这份方案 | 换一位操作者，只读 Space 和首版就能解释为谁完成什么、关键步骤为何存在、本版为何这样设计、交出什么及哪些假设待验证。退出重进仍可找回，Space 更新不改写该版原依据 |
| 2. 从首个具体案例走到一次可核对的方法迭代 | 先完成明确 Case 的真实执行、资产和 trace 阅读及评价，再依据真实问题形成候选和有界验证。运行、评价、诊断和版本演化按使用需要逐段补齐，不一次打包成全部页面 | 本次输入、准确方法、产物或失败可解释；之后能串起问题、证据、改法、验证及采用／不采用决定。独立评价检查业务成果、退化、人工介入与成本；候选失败也能有依据结束 |
| 3. 达到可用标准的方法进入持续业务 | 在约定业务范围中使用已接受的方法，纳入后续真实 Case、延迟反馈、例外、人工介入与周期复盘；候选验证保持独立 | 多个实际任务的结果支持其使用范围，用户能得到可用成果并继续工作；对未参与改法的案例也有观察。若尚无可用方法，继续有界诊断或停止投入，不以时间到期宣布稳定服务 |

这三个里程碑分别验证业务理解能形成方法、方法能依据实际执行改进、能持续产生业务价值。前一个通过不能代替后一个；不因某次候选没有改善而隐藏结果或强制采用。

它们按实际依赖推进，可以回访和交错：形成足以检验的首版后即可选择案例，不等待所有长期问题有答案；真实执行可能要求修正 Space 的业务理解或方法设计。已有历史继续可读，已采用方法也不因新候选研发而停止服务。阶段验收分别检查人的理解路径与 Agent 的实际工作，阶段化不变成所有日常用户必须重走的向导。

#### 第一批怎样落地

当前只集中完成生命周期的前两步。先以一个实际 Space 的现有材料和已确认业务要求形成真实内容，再把它变成可持续使用的产品能力；不只给页面增加栏目，也不把通用 agent-workflow 的产品目标当作这个 Space 的业务目标。

1. **形成并使用 Space 业务理解。** 写清具体问题、使用者和情境、想得到的结果、范围与成功条件；基于当前证据说明关键业务步骤、为什么需要它们、已有想法与待验证假设。人和设计 Agent 可以保存、阅读、讨论、修订，并保留来源与变化。此处的业务步骤不预先锁定技术节点或 Agent 数量。
2. **据此形成首版设计与准确版本。** 说明本版具体解决哪部分目标、为什么采用这些步骤和职责、每步交付什么资产、怎样交接、关键取舍及完成／停止／评价办法。把当前业务理解的准确引用、这份设计说明、方法图及配置连接起来；未定时保留草案，形成准确版本时固化依据。旧版本不改名为新首版，不补造历史动机。

本阶段结束时，人无需另翻聊天就能从 Space 连续读懂首版的设计缘由；设计 Agent 经 skill＋CLI 获得同一份已保存上下文，能继续修改草案或准备下一步。更新 Space 理解后仍能回看首版当时依据，尚未运行与当前不可执行等状态清楚。历史缺失保持未知，同时允许把当前有依据的分析作为新内容保存，而非永久停留在“尚未记录”。业务理解和版本设计的规范见[首版设计依据](product.md#首版也要保存为什么这样设计)。

验收先看正文与关系是否真正帮助理解，再核对保存、刷新、返回、版本引用和 Agent 读取。案例／实际资产图、完整评价分析与谱系作为后续使用阶段展开；已实现的图、CLI、运行及评价能力保留复用。浏览器与 CLI 维持权限边界，优先用既有资产或文档修订机制，不预设新的数据库表或完整富文本编辑器。

验证记录：共享底座 307 项测试通过（57 项环境相关跳过），工作台 UI 36 项通过，creation 185 项通过（12 项跳过）；Node 24 构建、消费者类型检查、文档 86 页构建及确定性示例通过。隔离 fixtures 覆盖无 run、缺失动机／定义、未知采用、不可执行；真实页面验证版本切换／刷新／返回、节点合同、预期资产及旧失败运行正文。47 张 `ws_*` 表前后行数与内容摘要一致；未运行业务模型，未发布、采用或改写历史。预期资产布局已压紧，后续两批及业务效果仍未验收。

#### 实际调优前需要定下什么

第二里程碑先用一个明确 Case 检验首版，准备准确输入、可执行版本和运行预算／停止条件即可，不要求先有 A/B 计划。真正进入方法调优时，再选择一个有业务意义的问题，固定业务标准、被评资产、判者、可比输入、允许改变的因素与验证边界。现有旧版本因部署指纹不匹配而不可运行，必须保留历史并登记新的匹配部署；条件变化是否允许作对照单独说明。评价者也可能出错，需要用已有明确正反例核对标准，而非直接优化一个未定义的总分。

设计 Agent 负责观察、诊断和形成候选；执行节点完成业务；Evaluator 提供证据；采用继续走现有人类授权入口。设计 Agent 的 session trace 先保留，未来用于提升设计 skill；本阶段不建设统一设计 trace 数据库或自动 skill 优化器。

#### Dogfood 与后续建设如何进入计划

真实路径中的共享能力阻塞可以插入相应批次，记录受影响任务、证据、最小修复与原任务复验方式。例如缺少准确资产关系就补该关系，缺少可取证的调用记录就补对应采集／读取；不能只因提出 issue 就扩成整套基础设施重建。非阻塞问题留在项目队列按价值、依赖与代价排序。

通用 Agents SDK、大媒体／生产对象存储、多用户部署、第二业务复用，以及设计 skill 的系统性优化，按具体任务需要另行规划。临时 VM、通用拖拽编排、版本自动总评分及全自动采用仍不作为本阶段交付。执行批次由执行 session 完成，认知侧从原任务独立体验、核对原因与决定下一步，用户继续判断业务用途和重要取舍。

### 已完成的业务批次与后续方向

**第 3 项的一条普通新业务路径已完成限定范围的独立验收。** 用户确认沿用 Kimi/GLM 历史材料；已完成授权归档清理，以及“新建业务 → 准备准确输入 → 显式运行 → 读稿及内审 → 外部认知 Agent 处理建议 → 重开恢复”，不要求 A/B 计划。唯一一次 Luna/high 运行产出研究、初稿、冷读、核查四项资产，主编响应 JSON 解析失败；运行仍失败、没有流程终稿、没有重试。认知侧实际读完产物，在 UI 保存准确过程稿及两条意见对应的修改建议，独立核对入库，并完成桌面、案例重新进入和390像素窄屏恢复。外部建议与可信节点评价分开，作品未接受、方法未采用；相关回归通过不代表内容质量合格。详见[本轮范围与结果](space-frontend-implementation-plan.md#当前阶段普通-content-新业务闭环)。下一项产品缺口是以案例输入和主要产物为入口，分开日常使用与工作流开发；目标定义已更新，完整导航和案例画布尚未实施。

1. **产品、交互与技术方案已完成本轮规划。** 覆盖日常业务和方法改进两条闭环，明确生命周期与工作台／四类图视图分工、画布内信息与动作、共享前端包、宿主适配、HTTP 读写和增量更新。只读草图已标注 MiMo 快照来源和未接通动作，认知侧已实际检查限定路径；产品判断继续接受真实使用修正。
2. **接入一个完整纵向路径。** Space → 方法版本全图 → Case/run → 节点轮次 → 资产阅读与返回；修正误导状态，复用现有存储，不另造 creation 后台。用已有 MiMo 三稿、研究复用及额度失败真实记录验证，不依赖新增模型额度。
3. **接通实际业务与资产工作。** 业务要求、材料挑选／导入、准确输入、显式启动、运行中断处理、评价和结果交付连成一条路径。资产工作台支持版本、来源、对照与复用；新材料不改写历史。只读路径可用不能宣布本项完成，已存在的服务能力按缺口接入。
4. **接通迭代工作。** 版本演进、验证集合、四问、比较、问题假设和采用共用同一对象上下文。既有底层第 4 步能力保留，补足整体产品入口；不能将所有比较功能重新记为未实现，也不能称整个工作台已经完成。
5. **把已完成的配对用于下一次明确决策。** 本次 MiMo 单案例阅读与迭代路径已独立复验，局部机制收益伴随表达代价，两边均未收敛；处理决定与审阅来源／跨轮一致性的下一假设已保存。下一轮先登记准确可执行部署，再决定是否验证这个假设；没有新授权的实验范围时，不自动追加稿件、扩大样本或采用。完整运营仍按前述缺口建设。
6. **按真实需求扩展。** 一般 SDK、对象存储、历史部署和生产认证独立排序；复杂分派通知、外部发布与大媒体治理逐项建设。单 CONTENT 完整可用后再讨论 B3、多 workflow 和第二项 FDE 业务。研究与分析不强制迁移，临时 VM 后置。

## 生命周期规划新增但尚未完成的能力

当前只读整改批次不自动包含以下全部实现：首版设计理由与业务目标的关联；稳定运营的观察窗口、纳入规则和周期复盘；关键节点跨 Case 的阶段资产集合与评价覆盖；版本变更和问题／验证／运营反馈的完整证据链；认知 Agent 的按范围证据包与修改复验回执。产品与交互已明确这些需求，现有数据可复用的部分先接入，缺失语义与查询分批补齐。没有真实一周使用记录时不伪造该项验收，模型后训练不作为首期依赖。

## 既有调优修复

以下是历史调优中已落入当前实现的修复，保留用于解释设计，不代表目标底座已交付。详细过程见[调优案例](tuning-loop.md)。

| 问题 | 现象 | 现在的支持 |
| --- | --- | --- |
| 同一次执行里重复的 step key 被静默 replay | 修订轮复用了 `draft-1` 这个 phase key，第二轮直接拿回第一轮结果，流程报告“已改完”，稿子没变 | `phase`/`agent`/`task`/`call`/`map`/`parallel` 的 key 在一次执行内重复即失败；失败后同 key 重试仍允许；恢复时照常 replay |
| 无法指定 Codex 可执行文件，记录的版本不是实际运行的 | SDK 自带的 CLI 拒绝新模型，只能靠自定义 factory 换可执行文件；trace 仍记录 PATH 里 `codex` 的版本 | runner 选项 `codexOptions`（含 `codexPathOverride`）；未给 `cliBinary` 时按实际可执行文件记录版本；`runtime.json` 记录可执行文件路径与合并后的配置 |
| 角色环境无法按 Agent 设置 | 仓库 `AGENTS.md` 被注入给写作角色，工程汇报规范进了内容 | Agent 配置 `codexConfig`，合并在 runner 配置之上，例如 `project_doc_max_bytes: 0`；只有设置了才进入 fingerprint |
| 模型不可用要到 run 中途才发现 | 账号不支持的模型在 run 里失败，宿主 Agent 接手手工完成 | `probeCodexModel`：只读沙箱、一次极短调用，返回可用与否、CLI 版本和拒绝原因 |
| 读 trace 靠各项目自己写脚本；按修改时间找会话会找错 | 调优脚本按最新修改时间取会话，拿到了同机另一个项目的会话 | `summarizeCodexAttempt`（命令、失败退出码、搜索、改动文件、错误、字符与 token）和 `codexSessionFile`（按 thread id 定位） |

## 仍需处理的具体问题

| 问题 | 证据 | 目前的做法 | 候选方向 |
| --- | --- | --- | --- |
| 用户级 `~/.codex/AGENTS.md`（约 1.2 万字）无法按调用关闭 | 关掉仓库文档后，内容角色的首条注入仍有这份工程协作规范 | 在内容角色 prompt 开头声明它不适用 | 为角色提供隔离的 `CODEX_HOME`（`CodexOptions.env`）。难点是登录凭据也在其中，不能随意复制；需要先确认 CLI 支持的只读引用方式 |
| 角色能看到未授权的工具与用户级 skills | 设计师角色在沙箱里读了用户级浏览器 skill 并尝试打开浏览器，最终超时 | prompt 明确禁止截图与浏览器；工具提示先在 Agent 沙箱实跑 | 调查 Codex 的 feature/工具开关，在 `codexConfig` 中按角色关闭；结论需要以 trace 验证，而不是以文档为准 |
| 角色的“防什么失败”只存在于消费项目代码里 | 文档和工作台需要列出每个角色的目的与所防失败，目前由消费项目各自维护 | 消费项目的角色规格里保留 `guards` 字段并生成文档 | 由共享定义与工作台提供目的说明的扩展约定；字段与是否参与指纹按实际语义设计 |
| 审阅者校准没有通用工具 | 审阅者先后出现过太松与太严，需要用正反案例检查其判断 | 消费项目自带校准脚本 | 共享评价模块记录校准案例、标准版本、判者与误判；业务提供判据，不能由库宣布普遍校准完成 |
| 同一 SQLite 账本上不宜并发运行 | 账本使用 `delete` 日志模式，并发写入有锁冲突风险 | 旧消费者同一账本一次只跑一个 run | 保留既有适配器使用边界；新资产 harness 采用 PostgreSQL，当前已实现并验证共享任务领取与并发，不把此能力追认给旧 SQLite 适配器 |
| 在消费仓库里运行本仓库测试有两处既有失败 | `runner.test.ts` 的 SDK 版本期望、`read-model` 的包解析，都依赖本仓库自己的 `node_modules` | 在本仓库独立 checkout 中运行 `npm run verify` | 让这两处测试不依赖安装布局 |
