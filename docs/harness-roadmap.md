## 从空工作台验收设计能力

**总目标：在保留旧历史的前提下，从一个没有业务理解、方法草案、准确版本和 Case／结果的新 Space 出发，设计 Agent 基于真实请求、材料和已声明的可用能力，经设计 skill＋CLI，形成有来源的业务理解和有专业方法的工作流设计包；人和接手 Agent 能在普通前端理解它，关键设计真实落实为可核对的执行定义，并能在有界任务中验证、修订和保留历史。**

“空”是业务记录为空，通用代码、schema、工具和经过明确选择的业务能力可以复用；不得自动灌入旧 CONTENT 方法或旧成果。本轮已接通新 Space 创建和独立设计能力修订；当前 CONTENT 示例通过明确的能力提供方编译五项职责与交接。共享保存、查询和候选合同可以复用，不能据此声称任意业务拓扑或任意工具已自动生成。按需补共享能力或标准扩展接口，不要求构建任意自然语言到代码的自动编译器、通用拖拽编辑器或新的一套状态库。设计包的内容和工作次序由[设计指南](designing-workflows.md#设计-agent-与工作流设计包)维护，前端由[工作台合同](workbench-presentation.md)维护。

### 必须用任务检验的九项要求

以下每项记录通过／不通过／未执行及准确证据；涉及独立结论的未知不能填成通过。不适用须说明业务理由和影响，不能通过删掉困难任务改变目标。验收样本、关键判据和停止条件在执行前固定，改变时保存新修订，不回写原判据。保留设计 Agent 获得的原始业务输入、实际使用的方法／skill、自己形成的方案及 CLI 写入证据；别人预先写好方法、它只负责保存，不算设计能力通过。负责人本轮可以按用户要求兼任设计 Agent，但必须明确角色，并把外部指导、审阅纠正与后续人工补做分别记录，不声称未经帮助的独立发现。

| 编号与目标 | 实际怎样验收、留下什么证据 | 不通过的典型情况 |
| --- | --- | --- |
| **A1 空 Space 与真实业务理解** | 记录初始业务对象为空。负责人用 skill＋CLI 建立理解并保存：为谁提供什么价值、场景、范围、业务关键判断、成功／失败标准、来源和未知。普通前端独立阅读后核对同一修订；旧 Space 保持原样 | 必须开发者先塞入固定五节点才能开始；只换旧目标标题；把底座开发目标写成具体业务目标；依靠数据库注入完成正常用户路径 |
| **A2 专业方法足以指导工作** | 选择代表任务和一个会改变做法的困难情形，实际走查关键工作，留下可读产物、判断依据及处理差异。每个关键步骤说明怎么调查／判断／制作、依据、缺失与冲突处理、交接及完成条件；比较选中结构与合理替代，说明成本和取舍 | 只有角色、流程顺序、形容词或格式字段；无法处理例外；要求都很高却没有兑现方法；凭 Prompt 长度、节点或审阅者数量证明深度 |
| **A3 设计、图与执行定义一致** | 为所有影响结果或运行边界的关键决定建立“目标／依据→方法及责任→具体 Prompt／skill／上下文／工具／程序或路由→检查办法”对应；从准确候选双向核对。完整工具定义、输入输出、模型与预算可读；缺失实现明确阻碍可执行 | 正文要求 A，实际沿用 B；设计变化只改变版本名；图中有不存在的能力或回路；把旧版本缺失信息用当前配置补造 |
| **A4 节点与交接能应对反例** | 用受控样例检验关键工具和交接。至少覆盖本方法最主要的缺料／矛盾输入及校验／工具失败风险；核对允许信息与隔离信息、输出解释与来源、失败定位、局部修复或诚实停止、预算。先保存原响应及修复来源 | 只验证 JSON 能解析；把不可用工具当可用；一次可恢复格式错误让全部业务失去诊断；无限重试、静默猜值、把工具返回或人工补做当正式模型产物 |
| **A5 普通前端可独立理解** | 负责人亲用；再让未读设计聊天或 CLI 答案的接手 Agent 从普通入口找到目标、理由、完整 Archify 图、节点方法与配置、资产交接、验证方案及状态，解释为何这样做与下一步。实际点选、追来源、返回和重开，之后再用 CLI 核对 | 只能靠准确深链接、作者口头解释或底层 JSON 拼出主线；图不可点、长文不可读、范围丢失；CLI 有信息便替前端宣布通过 |
| **A6 验证计划先于结果** | 保存准确样本／材料、关键和最终产物标准、判者、反例、预算与停止规则，列明要检验的假设。程序检查、独立审阅、模拟诊断、用户接受与真实业务效果分别定义；需要比较时先冻结基线和可比条件 | 看完结果才挑成功标准；用内部 pass 或构建成功代替质量；只有成功样本；无基线却宣称改进、无真实反馈却宣称观众受益 |
| **A7 行为变更与旧版保留** | 选一项确实影响行为的设计决定，经 skill＋CLI 保存修订并形成有依据的新候选；核对实际配置／路由／交接相应改变，受影响检查重做。原理解、设计、版本及已有 Run／评价仍能按原内容重开，前驱与差异可解释 | 只改文档或复制版本标签；新认知覆盖旧版；查看候选就改变采用；为展示谱系伪造版本或运行。修辞修改不能充当这项验收 |
| **A8 被验设计包真实运行** | 在执行可用且条件明确时，由负责人通过 skill＋CLI 以本轮实际设计、落实并选定的准确版本发起一个有界真实 Case；从前端亲读关键产物及最终结果或失败，核对实际指令／输入／调用／产物与该版设计一致，记录预期与实际差别、人工补救及用量覆盖。A7 若另生新候选而未实跑，仍标其运行与行为效果未验证 | 实际调用旧工厂／旧配置却归给新版；用另一版本的运行抵扣被验设计；负责人流程外写好作品再算 workflow 成功；仅靠执行摘要或测试代替运行。只走到失败路径，就不宣称成功或返工路径已验证 |
| **A9 证据能进入下一次设计** | 从 A8 的实际结果保存有依据的评价与处置，区分修本次作品、补材料、改方法、校准评价者、harness dogfood 或暂不改。引用 workflow trace；另保存设计 session 的操作／决定／产物索引供改进设计 skill。通用设计 skill 另用一个未透露答案、约束不同的有界任务检验迁移 | 每次问题都加 Prompt 或节点；只复制 CONTENT 模板；没有新证据便宣称改进；把两类 trace 混为一份有效性证明；要求读到模型内部推理或完整外层自动入库才能继续 |

A2 的专业方法走查可以由负责人以设计 Agent 身份完成，但不能归作工作流运行，也不能以代存别人的方案通过。A4 还要对质量风险最高的节点做一次有界能力试做：使用候选的实际指令、上下文和工具，亲读输出，看它是否完成指定的专业判断及交接，不能由负责人临场补写后算节点通过。未获得运行条件时保留待验证，不用纸面推演冒充；实际调用沿用明确预算，不扩充无关试验。节点能力试做、确定性检查和 A8 的完整真实运行分别记录。反例应能改变关键设计决定，避免只换标题、数据或措辞。接手 Agent 的独立阅读用于发现解释缺口，不代表用户已接受设计。A9 的迁移检查只交付业务理解、方法理由和方案映射，不要求另建 Space、前端、部署、业务模型运行或长期经营；不建设第二个业务产品，也不由单次通过推定普遍能力。

### 各阶段到什么程度才可以继续

| 结论 | 要达到的范围 | 尚不能宣称什么 |
| --- | --- | --- |
| **阶段 1：业务理解可继续设计** | A1；业务与方法层的关键未知已定位，足以提出可检验方案 | 具体方法已成立、已自动生成或业务有效 |
| **阶段 2：设计包可交付试跑** | A2–A7 中设计、交接检查、候选变更与阅读路径通过；关键执行阻碍已解除，准确首版可登记并匹配部署。A9 的设计 session 引用与后续证据位置已安排 | 模型产物达标、方法已改善、已获采用。允许将高风险节点试验提前，但另记预算和范围 |
| **阶段 3–5：完整设计到验证路径成立** | A8 真实执行及 A9 评价、分流、修订贯通；质量不足如实记录。需要候选对照的分支按原阶段 6 验证 | 首轮失败不能包装为业务成功；一次成功或一项迁移样本不能证明普遍稳定 |
| **业务质量与持续有效** | 逐 Case 达到事先规定的标准，有真实接受／业务反馈；改法有对照与适用范围，长期结果按阶段 7 观察 | 不能由前端、存储、trace 完整或多 Agent 一致替代 |

**关键条件不以平均分抵消。** 正文与执行不一致、来源或身份造假、关键业务路径走不通、历史被覆盖、依赖越权或没有约定运行边界，均阻止对应阶段通过。普通视觉小问题按实际影响记录，不与业务阻断混为一类。失败时明确是专业方法、内容、产品接口、展示、运行环境还是证据不足；先保留竞争解释，再把有步骤、证据和通过条件的修复交回责任方。

负责人负责业务判断、专业方法与实际使用结论；原执行 session 负责共享能力、集成和修复；独立核对者检验遗漏与接手路径。负责人既是作者又是判者时必须记录这一点，并用独立阅读及真实结果限制自评。验收记录只需保留规则编号、准确对象、动作与读到的内容、判断理由、证据位置、失败／修复和覆盖边界。**本轮验收状态如下；“通过”只覆盖对应行所列任务。整体 A1–A9 尚未通过。**

## 下一轮先完成什么（2026-10-12）

**近期目标：让一条真实 workflow 从有理由的设计，走到准确执行、成果判断和有依据的改进决定。** 当前内容样本用于验证这项共享产品能力；本版的完整业务产物是有依据、可连续阅读的完整中文稿，文字到视频及真实发布仍属于更长的业务周期。既有 A1、A2 和设计阅读成果直接复用；不再为了推进重造空 Space，也不以通用功能数量作为本轮结束条件。推导依据见[方法与 harness 怎样分别验证](../../../docs/product-understanding/learning-and-dogfood.md#怎样判断下一步值得做)。

10 月 12 日负责人从普通工作台进入当前设计草案、阅读理由并预览候选：页面明确显示尚无匹配部署。随后 CLI 核对，当前两个已登记方法均为不可执行，原因为发布配置与现行 provider 不匹配。它们的历史仍有效；这项观察不能单独确定是哪次变更造成，但足以说明**先核定当前执行条件，再测试研究改法**。共享 SDK 迁移和其他消费者运行不替代该方法的准确核验。

当前最大的产品未知是：设计中的专业做法能否在真实节点和交接中发生，结果能否被正确判断，候选能否带来值得保留的变化。请求准备和证据概要已经减少操作负担；继续扩展通用管理功能不能直接回答这些问题。下面批次连接既有七阶段，不新增另一套生命周期。

| 批次与要回答的问题 | 具体交付 | 我怎样实际验收／何时停止 |
| --- | --- | --- |
| **1. 固定可执行的比较条件**：到底测试哪份方法、在哪个环境？ | 经检查的代码／配置基线；在当前环境保留旧业务方法的控制版与研究候选；业务改动和环境改动分别列明；准确输入、判据、工具权限、部署、预算和逐 Case 放行条件 | 对照设计、实际指令和部署身份，从前端与 CLI 读到一致依据。无匹配部署、权限或明确预算即不运行。控制版是迁移后的新版本，不能冒充旧版复跑；旧资产及评价保留 |
| **2. 验证关键节点和评价者**：研究改法是否解决原问题？ | 原数量歧义样本及一个会改变结论的反例；同环境、同输入的控制／候选结果；关键主张回原文、跨答案一致性及未丢必答内容的检查；评价者的已知正确／错误／不足证据检查 | 亲读实际输出和来源，核对方法是否兑现；独立判者核对证据，不以多数票定对错。关键判据失败就留在节点诊断；保守地删去必答内容不算通过。单次成功不宣称稳定提升 |
| **3. 完成一个真实 Case**：局部方法能否形成完整业务结果？ | 使用通过节点门槛的准确版本完成研究、成稿、审阅及必要返工或明确停止；保存各阶段资产、实际依赖、失败及人工介入 | 从普通前端读完整稿和中间成果、追到图中生产节点及原材料、阅读评价与处置、离开重开，再用 CLI 核同一事实。流程外由负责人补写的成果单列；真实只覆盖失败分支时不宣称成功路径通过 |
| **4. 完成一次有根据的迭代决定**：应该改什么，是否保留候选？ | 把完整 Case 的差距分流为作品、材料、方法、评价者或 harness 问题；需要改方法才生成后继，并按冻结条件比较；保留收益、退化、分歧与代价 | 从候选回到具体问题和原结果，沿版本关系核对实际变化。可以决定继续验证、不改或不采用；只有证据及授权满足时才限定采用范围，不能用登记新版本代替决定 |
| **5. 检查初步复用**：离开调优样本还能工作吗？ | 用一个未参与改法的同业务新 Case，检查原方法边界、结果、人工负担与新增例外；长期采用另设真实观察窗口 | 不靠逐条提示修正完成专业工作；失败能定位、能保留已有成果并继续处理。一个新 Case 只证明初步复用，持续经营、跨业务适用与用户接受仍需各自证据 |

第一批交付应是一份**可审阅、可执行的试验包**：控制版／候选的准确身份与差异、输入与反例、评价依据、调用／时长限制、停止与失败处理，附当前前端阅读入口。执行 session 完成集成、隔离检查和可复现交接；认知负责人核对后在明确运行条件内执行、亲读和裁决，未通过交回同一任务。原 release、额度与时钟不会因草案或计划更新重置。本次规划未发起业务运行、登记、采用或定时跟进。

### 哪些工作并行，哪些延后

**并行的小范围 dogfood：** 原文／评价依据无法抵达、关键身份或状态错误、运行条件无法核对，阻塞上述任务时先修。慢读取先测单接口、重复取数及并发影响；请求数、返回字节、模型调用、耗时与人工补做分别记录，未知费用不补估成实测。每项优化都回到原任务复验；不先选缓存或重构方案。R2 保持已有隔离技术证据，真实附件阅读与恢复在对应任务需要时验收；没有媒体需求不提前引入大媒体管线。

**暂缓：** 通用拖拽编辑器、任意自然语言自动编译工作流、自动总评分／自动采用、设计 session trace 统一入库、完整 SDK 能力覆盖及第二业务产品建设。通用性先通过不同约束下的设计迁移和现有消费者合同检查，不能从一个 CONTENT 五职责模板推断出来；需要新拓扑或工具时再按真实需求扩展 provider 合同。

阶段推进看四类结果：工程可靠、用户任务可完成、业务成果合格、后续使用仍有效。负责人自评、独立 Agent 审阅、用户接受与真实经营反馈分别记录。**这轮最值得得到的结果，是能解释一条方法为什么有效或为何仍失败，并有证据作下一决定；不是把七个阶段都标为通过。**

## 下一步按什么顺序推进

下面七阶段是长期的生命周期与验收地图；当前执行优先级以上节批次为准。既有通过项保留原范围，变化影响哪些条件就复验哪些任务，不能直接抵扣新版本验证，也不机械重走全部步骤。CONTENT 仅作当前使用样本，通用能力属于 agent-workflow；已实现的功能直接复用，不从零重造。

| **6. 验证与采用决定** | 有范围的案例与标准、基线／候选准确版本、全部尝试与比较、收益／退化／成本、采用或不采用依据；版本关系图可追到证据 | 在明确条件下实际比较候选与基线；从比较与版本关系图追读原稿、评价及失败，判断适用范围；核对查看候选不会更换日常采用版 | 能有依据作采用、限用、继续查证或不采用决定；候选不必胜出，技术通过不等于质量改善，采用由有权主体执行。**当前：单案例配对基础已有，完整产品路径待验收** |
| **7. 持续业务与周期复盘** | 在采用范围内处理后续真实 Case，查看窗口内全部相关业务、关键资产、反馈、失败、人工负担和评价覆盖，保存继续／限用／回退／新一轮改进决定 | 使用采用版完成后续实际业务；按事先说明的窗口与样本纳入规则复盘，包含未参与调优的案例及反例，追到具体结果与处理记录 | 产品能支持持续工作，证据支持使用范围；短期功能可用与长期效果分别验收，没有真实观察期就记“待观察”。**当前：未通过，随前阶段成果建设并积累证据** |

阶段 5 可以决定不改方法；只有选择候选研发的分支才进入阶段 6 的方法对照。没有候选时保留诊断与处置结果，不为阶段验收强造新版本。

阶段是建设与检验的组织方式，不是每个用户都必须重走的向导。阶段 1、2 达到足以测试的清晰程度即可进入 Case，不等待所有未知消失；真实结果可以推动返回业务理解或设计。日常运行、候选研发可以并行，方法不需要为了完成表格而升级。

## Harness 操作成本优化（2026-10-12）

本轮改善设计／观察 Agent 使用现有底座的成本：把请求组装交给 CLI，让运行证据先以有界概要呈现，再按问题深入。当前业务质量结论不变：研究节点试做未通过 V3，完整 Case 未运行；CLI 更易用不能抵扣这两项。

| 真实阻力 | 本轮改动 | 验收任务 |
| --- | --- | --- |
| 保存能力与设计时手工搬运修订、hash、署名、提交依据，曾因字段和输入形状错误失败 | 准备并预检请求，输出可审阅的私有文件，继续使用已有 save 接口 | 用现有业务正文准备请求，无手算 hash、无临时组装脚本；显式历史依据不被换掉；同一准备结果可复检；冲突明确且没有隐式 POST |
| 理解一次运行需跨命令拼接身份，过程输出夹带整份方法定义 | `run-evidence` 复用已有安全读模型，默认概要、指定节点后再展开 | 从真实 Run 判断准确输入／版本、执行范围、实际产物和缺失；多尝试与程序步骤不串线；失败或截断不包装为完整证据 |
| skill 重复讲解接口机械细节，普通操作也容易变成完整验收仪式 | 项目内 skill 使用新 CLI，保留专业判断、范围和证据限制 | 接手 Agent 依据 skill 与返回的阅读入口完成任务，不需要查实现源码；产品验收与日常读取的检查范围分开 |

**状态：CLI 与 skill 已实现，负责人已完成真实 Space 的请求准备、复检和证据阅读核对。** 五个节点的指令与 schema、验证计划共 11 份原文及 hash 保持一致，设计正文与 8 条来源保留；复检不改文件或幂等键，错误 hash、过期提交依据、错误引用 hash 和重复覆盖均被拒绝。准备／复检只有读取和本地私有文件操作；与原有 save 的兼容由隔离测试验证，没有在业务 Space 制造验收修订。

同一真实运行的**概要定位任务**，旧路径需 `run`＋`process` 两条命令、3 次 HTTP GET，输出 34,727 字节；新概览一条命令、4 次 GET，输出 11,874 字节。准确运行／版本／输入、实际节点与产物、程序与 Agent 计数及过程缺口一致；整份方法定义和尝试详情留待按需阅读。指定研究节点后可读准确 Agent／程序尝试与 runtime 概要；trace 首页明确是预览。负责人再沿返回入口亲读研究资产正文、关系和既有诊断。**这证明减少了手工拼接与上下文输出，不证明后台请求减少、端到端加速、token 或业务质量改善。** 构建、类型检查、62 项相关测试及文档检查通过。

独立接手 Agent 能凭新 skill 还原研究试做与程序保存的范围、识别部分覆盖，没有将技术完成当业务通过。其初轮正文下钻在并发读取窗口触及验收包装器的 15 秒超时；随后单独补验，顺序读取资产正文、该资产的冻结评价标准和已有评价均成功，完整走通概要到判断依据的阅读链路，并区分自己读到的事实、已存评价与尚未核对的原始材料。该延迟现象记为后续 dogfood 线索，尚不能定位到新 CLI；下一项效率验证应分开测接口耗时、重复读与并发影响，再决定是否需要更轻的服务端投影或复用已取得的概要。阅读路径通过不等于业务质量通过。

本轮未新增业务模型运行、重置原预算、改写旧版本或成果。所有对照与失败记录保存在私有验收目录；公开文档只保留结论和测量口径。

新接口说明集中在 [Operator CLI](operator-cli.md)。后续依据真实失败决定是否补恢复指引；不为易用性另建状态库、权限系统或自动采用流程。

## 2026-10-10 验收范围纠正

以下阶段 1–4 的历史记录保留发生过的操作和业务结论，其中“通过”仅说明当时列出的局部路径，**不再作为整体产品体验通过或继续推进的依据**。此前验收过多依赖准确深链接、已有背景知识和程序读取，把能找到数据、完成保存误当作人能自然理解并继续工作，没有完整落实已经确认的导航、Archify 主画布和阅读返回约定。这是验收范围与判断失误，不能归因于用户未说明要求。

重新验收从普通入口开始：先记录一个真实任务如何完成、页面本身支持了什么判断、哪里需要外部解释；再核对内容与准确事实。阶段 1 先完成业务目标／成功条件／完整周期／当前方法范围的理解、CLI 修订后的前端读回、返回和下一步导航。前端编辑能力不作为门槛。发现阻碍即退回原执行 session 修复，复验当前任务及相邻路径后才进入阶段 2；不为走完阶段表跳过体验缺口。

复验发现并修复了侧栏布局、阅读位置、目录遮挡来源、来源无法打开既有资产／Case，以及新增返回条挤占正文的问题。负责人实际打开研究原文，沿对应 Case 阅读唯一失败运行的未发布响应，再返回准确理解并刷新，来源展开与阅读位置恢复。通过范围仅为本阶段这条真实路径，不代表阶段 2–4 整体体验、长期效果或用户接受；无法解析的文档类来源仍明确显示引用与限制。

## 阶段 1 操作验证记录

2026-10-09，认知负责人从真实 4397 前端读完业务正文与来源，能够解释内容业务为谁提供什么价值、为什么需要研究／完整表达／读者理解检查／事实核查与返工，以及现有证据与未知的边界；另由独立核对者检查业务资料一致性。

实用中发现一句话把 Case 输入变化与 Space 长期目标变化混在一起，负责人通过前端作了有理由的修订，声明 Agent 作者。保存后刷新、离开再进入均恢复新正文；历史深链接刷新后仍保留旧文。CLI 读回与前端保存正文逐字一致，前驱与来源准确；负责人再经项目内 skill 和 CLI 保存来源补充，前端读到同一新修订。来源文档的内容摘要也已核对。

**结论：阶段 1 的阅读、形成／修订、保存、恢复、历史保留和人／Agent 共用上下文路径通过。** 内容仍是未确认的 Agent 理解；真实读者效果、方法设计是否有效及长期经营价值尚未验证。没有启动业务模型、发布或采用方法。准确修订、实际操作与截图等证据保存在私有验收记录，不把这些内容复制进公开文档。

**结论：阶段 2 的设计阅读、草案修订、准确首版登记、图与详情及当时依据保留路径通过。** 此处正文是 Agent 提出的待检验设计，准确首版没有可执行部署，0 次运行、未验证、未采用。后续草案没有另行登记为首版，也没有覆盖原版。本轮没有业务模型调用。

首版选择只使用给定材料；输入 schema 仍可表达联网选项，接入实际部署时必须落实禁止联网，不能把文字约定当执行约束。模型适用性、输出质量、返工净收益和真实读者效果留待真实 Case。准确身份、操作正文和截图保存在私有验收记录。

## 阶段 3 实用验收记录

**本段要完成的任务：让阶段 2 的方法进入一个真实、范围明确的 Case，能从准确输入一路读到实际过程、成果或失败。**

1. 接通独立 Space 的准确方法与真实执行部署，复用现有任务、存储、资产和 trace。核对模型、执行器、定义指纹及工具权限；落实本版只用给定材料的限制。若必须改变冻结方法声明，保留原版并形成有理由的后继版本，不能原地改写或让不匹配的部署冒充原版。
2. 准备一个有来源的实际 Case，冻结原问题、读者目标、必答问题、材料和有界预算。旧 Case 仅作输入或经验来源；不得把旧运行结果算作这次产出。首个 Case 不以 A/B 计划或采用为前提。
3. 经 skill＋CLI 准备、保存并显式发起准确 Case；前端从普通入口读回委托、输入、状态、全部 run、节点实际输入输出、准确资产正文、关系和执行 trace，退出重开保持上下文。关系以实际保存的依赖为据，未产出的预期资产、失败尝试、人工补做分别标明；重复提交不得产生重复运行。
4. 执行 session 先交付可用入口、准确部署、待运行 Case 及预算条件，完成隔离工程检查；认知负责人核对后通过 skill＋CLI 发起一次有界真实运行，再从前端亲读成果和过程、退出重开，核对同一准确事实。发现产品问题退回本阶段修复，不用执行摘要或模型自评替代验收。

使用现有授权与配置，不扩大付费调用、自动重跑或业务外发。失败时保留可诊断的真实证据；若只验证到失败路径，就准确记录覆盖范围，未产生的成果、关系和评价仍待验证。本阶段不伪造创作者接受、方法采用或长期效果。

2026-10-10 实际使用结论：负责人核对原五问、完整材料、准确方法、禁止联网及修订／调用／超时限制后，唯一一次前端启动真实 Case。研究稿已保存并亲读，研究→作者的实际依赖可追溯；作者原响应被引用校验拒绝，未成为稿件资产。期间没有自动重跑。

负责人发现 Run 已失败而节点仍显示运行中，以及必须翻阅大量事件碎片才能阅读原响应的问题。原执行 session 修复后，同一运行的图与节点准确标注派生失败及依据，旧技术步骤原状态保留；完整未发布响应可按内容目标、连续口播、逐段画面阅读，原 JSON 与准确会话／事件来源可展开。负责人重开验证全部 8 段正文，并用 CLI 核对 13 个阅读章节及原输出完全一致；冻结输入与研究资产未变，Case 仍只有本次一次运行。

**结论：阶段 3 在上述实际范围内通过。** 模型错误引用和稿件中的业务质量问题原样保留，交阶段 4 评价处理；不补造冷读、事实核查、主编或用户接受。修复改变执行桥接指纹，旧准确版历史仍可读但当前严格不可执行；再次运行须登记真实后继版本，说明改变和依据。暂不重跑，不自动采用。定时跟进保持删除。

## 阶段 4 实用验收记录

2026-10-10，认知负责人分别取得本人准确读取依据，读完研究五问及作者完整响应，按研究节点当时职责／冻结读者目标与完整稿标准保存两份独立四问评价。实用中先发现未发布响应、继而发现正式资产缺少外层 Agent 评价入口，均交回原执行 session 修复后复验，没有冒用人类身份。

负责人先记录作者稿需要修改，再在研究复核后追加处置修订，同时关联两份评价及各自读取依据。刷新、离开后准确重开，可从处置返回评价和原资产／响应；CLI 核对两份四问、处置理由、主体、标准、内容哈希和前驱一致，旧评价与旧处置原字段、冻结输入保持不变。Case 仍只有原失败运行，没有触发重跑、采用或外发。

**结论：阶段 4 在本次研究资产、未发布作者响应及失败处置范围内通过。** 业务结论是研究证据解释和作者内容均需修改；错误引用、前后证据混用、数量口径与实际结果交接损失进入下一阶段诊断。Agent 意见保留为未确认，不能据此声称真实读者理解、创作者接受或完整工作流成功。宿主身份与读取记录证明准确内容的交付，不替代实际阅读或证明完整外层思考轨迹。

围绕这一真实 Case，先说明评价什么、按什么标准、谁作判断、证据在哪，再记录下一步：

1. 对已发布研究产物、未发布作者响应及执行失败分别引用准确对象；未发布响应绑定原 run／occurrence／session／event，不为了能评价而伪造稿件资产。
2. 阅读实际内容，对照 Case 的完整五问与当前业务目标，记录满足、不满足和待验证之处。保留原判者与证据，Agent 判断不冒充真实读者或创作者接受，不强造总评分。
3. 保存有理由的处置，可提出修作品、补材料、校准判者、修 harness 或进入方法候选诊断；处理建议与实际执行分开。保存本段记录不自动重跑、发布方法、采用或外发。
4. 负责人从前端亲读成果与依据，经 skill＋CLI 保存有根据的评价和处置，再从普通前端入口重开，核对准确对象、意见和下一步；从记录能回到原输入、研究稿、未发布响应与失败。范围不支持的动作明确不可用。

规范依据：[产品生命周期](product.md)、[工作台展示](workbench-presentation.md)、[Operator CLI](operator-cli.md)。

## 2026-10-10 阶段 5 安排记录（历史）

本段先回答“哪里出了问题、可能为什么、下一步改什么以及如何验证”，再决定是否需要新方法。复用已有 issue、iteration、准确版本与图详情，不为一个 CONTENT 样本另造通用框架。

1. 从阶段 4 的准确评价与处置进入问题，分别保存观察事实、可能原因、支持／反证及未知。当前至少区分引用失效导致发布中断、研究中的证据时点／数量口径，以及已有研究信息在作者稿中丢失；不把事实与原因假设混写。
2. 沿问题追读冻结输入、研究稿、作者响应与相应 trace，比较输入质量、提示／交接、模型生成与校验恢复等解释。允许决定修作品、补材料、校准判者或暂不改方法；共享环境问题单列为 dogfood issue。
3. 若证据支持改方法，再形成有准确前驱、改动动机、具体差异、预期收益／退化和验证条件的候选。原准确版当前不可执行，部署指纹变化必须显式记录，不能改写历史或伪称与旧版相同。
4. 执行 session 交付可用路径和准确对象；负责人从前端实际追读评价、诊断与依据，通过 skill＋CLI 保存判断，再从前端重开核对。诊断路径通过后才进入阶段 6 的有界验证，不预先声称候选优胜或已采用。

本段不自动增加真实业务调用或外发；后续运行须有明确准确版本、范围、预算与停止条件。

## 每阶段发现的新问题怎样处理

| 问题去向 | 怎样继续 |
| --- | --- |
| Prompt、tools、节点或流程的改法 | 从业务证据进入阶段 5、6；skill 是一种表达方式，候选不强制做成 skill |
| 共享存储、资产关系、执行器或其他 harness 缺口 | 记录 dogfood issue 的原任务、证据、影响与依赖；当前阶段被阻塞时安排最小修复，再回原任务复验，非阻塞项排入后续队列 |
| 设计 Agent 自身的判断与设计方法问题 | 保留外层设计 session trace 与关联依据，未来用于提升设计 skill；暂不建设统一设计 trace 数据库 |
