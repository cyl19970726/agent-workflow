# 优化 Workflow：从证据到下一版

前置阅读：[设计](./designing-workflows.md)与[评估](./evaluating-workflows.md)。优化回答：哪个问题值得改、原因有哪些证据、改动预期改善什么、如何判断采用或放弃。它可以是人工与 Agent 共同推进的开发过程，不要求建立自动修改生产代码的 Agent。

## 从意图和评估结果定位问题

输入是当前意图及其版本、被测 workflow、评估结果、实际产物/trace 和基线。先判断问题是否妨碍用户目标，再判断该改哪层。评分下降或一次工具失败只是线索。

| 观察 | 需要核对的证据 | 可能的修改位置 |
| --- | --- | --- |
| 关键内容缺失 | 来源是否存在；Builder 是否获得/读取；原产物是否包含；页面是否展示 | 来源采集、方法输入、Builder 或阅读器 |
| Reviewer 没意见但报告有错 | 独立裁定、候选绑定、实际读取范围、校准结果 | Evaluator 方法或执行器；不能先宣称报告通过 |
| 断流后全批失败 | 原始错误、重试、子父运行和队列事件；恢复是否产生重复副作用 | 宿主恢复和调度，不把网络错误当内容差 |
| 耗时或返工过大 | 有效调用、重复读取、等待、修订结果及用户介入 | 流程边界、缓存、反馈定位或交接方式 |
| 分数改善但用户仍无法使用 | 成功标准是否覆盖意图、实际使用反馈及新旧需求 | 验收设计或目标理解，不能只继续提高原分数 |

上表是诊断方向，不是已证实因果。记录“观察 → 假设 → 验证证据 → 仍未知”；例如出现 WebSocket 错误可以证明某次断流，不能据此把其他所有失败都归因于网络。调查到可以选择一个有区分力的试验即可，不要求彻底解释底层系统才继续。

## 先区分修产物与改方法

一次报告遗漏可以按已授权的 repair 流程生成新版本；这不能直接证明方法更可靠。只有把改法在可比输入上重新执行并检查，才能评价跨运行改进。

反之，不能为了建框架而无限推迟可用交付。根据当前目标选择本次修复到哪份资产、验证到哪一步。保留有效旧结果；上游变化时让受影响的下游评估或综合过期，不让旧接受标记自动覆盖新版本。

## 一项改动对应一个可以推翻的假设

在现有主报告中记录一张实验卡即可，不要求每项新建文件：

| 字段 | 要记录什么 |
| --- | --- |
| 目标和问题 | 关联哪项用户要求、哪次失败或已裁定漏项 |
| 假设 | 改 X 会通过什么机制改善 Y；哪种结果会推翻它 |
| 处理与对照 | 基线与候选版本、唯一主要变化、不可避免的环境差异 |
| 不应退化的部分 | 原来成功的能力、关键证据、产物与用户约束 |
| 案例和信息边界 | 开发、校准、最终验证案例分别是谁可见；后来答案不得只给候选 |
| 预算与停止条件 | 最多运行/修订次数、时间或费用，证据不足时怎么结束 |
| 实际结果与决定 | 输入/产物摘要、run 引用、效果和代价、采用/放弃/继续查证及理由 |

减少调用、步骤或阅读的建议同时说明下限：什么必要输入、检查或交付必须保留。节省成本要在这些要求仍满足的条件下比较，不能把少读资料产生的遗漏算成优化。

## 选择能回答问题的实验

- **同题重做**：固定原需求时点、输入和交付节点，比较旧失败改善与旧成功退化；初稿对初稿，接受稿对接受稿。缺旧版本或投入记录时收窄结论。
- **对照实验**：相同候选/来源分别交给两个 Reviewer，或相同输入交给两个 workflow；一次主要改一个因素。记录实际模型、指导、工具、重试及人工介入。
- **消融实验**：去掉或替换某个步骤，验证它是否有贡献；只有不损失必要结果时才采用删减。
- **故障注入与恢复**：模拟断流、超时或进程中断，检查失败隔离、恢复、资产保留和副作用幂等。先在隔离环境验证，不故意损坏生产数据。
- **未参与改法的案例**：用保留集或新任务检查迁移。看过结果并用于修改后，该案例就不能继续冒充未见保留集。

同一模型也能进行不同方法的对照，不要求换模型；使用实际被允许的模型。反复比较容易挑到偶然好结果，应预先固定重复次数/停止条件，保留全部结果；时段和外部服务变化明显时交错或随机执行两组并记录差异。

案例中的具体答案、后来的用户提示和成品仅给评审侧；若候选新增了信息，则将其明确作为实验变量，不能声称只是方法变化。用前后版本评估同一批冻结产物可以比较 evaluator；优化 workflow 时应固定 evaluator。确需改评分规则时保存新版本，并让两版 workflow 的可用产物接受同一版规则重新评估。

## 每轮给出有范围的决定

| 决定 | 证据条件 | 后续动作 |
| --- | --- | --- |
| 采用候选 | 预先标准在指定范围内满足，关键能力无退化，代价可接受 | 保存版本及接受范围，按宿主升级策略推进 |
| 保留基线/放弃改法 | 无有效改善、不可接受退化或代价不合适 | 留下结果和否定原因，防止重复同一试验 |
| 继续查证 | 结果混杂、波动或缺失，仍有明确可区分的试验 | 在剩余预算内补最小验证，结论保持未定 |
| 等待必要输入/停止本轮 | 关键来源、权限或偏好缺失，或预算已到 | 保留现有产物，说明缺口和恢复条件 |

技术失败的比例计入可靠性结果，不能从样本中删除以抬高成功率；没有产物的案例不强行评分内容。有部分产物时可做注明范围的局部检查，但不能用它代替完整交付验收。分析质量时同时报告可评估样本数与原定样本数。

## 把学习保留下来，再回到设计

保存触发来源（Agent 自主发现、用户指出问题或提供修法）、关键证据、改动与裁定。将有效失败案例加入回归集，将经过迁移验证的通用方法写入项目指导；单次成功先保留为候选经验。公开仓库只保留脱敏方法和必要记录，不复制私有会话、凭据或研究资产。

更新 [设计报告](./designing-workflows.md)中的步骤、资产依赖和理由；维护同一个当前入口。工作台应能追溯意见 → 修改 → 复验 → 采用的版本，并保留否定方案和未解问题。既有成果继续可读，用户回来无需重新解释已经确认的要求。

先提交共享仓库改动，再由消费项目显式升级 submodule；修改语义时提升 workflow revision，新版本用新 run，旧 run 按旧定义恢复。相关 API 与恢复边界见 [编写指南](./writing-workflows.md)和[宿主集成](./integration.md)。文档、代码、示例通过不等于真实业务方法已验证，最终报告需分别给出这些状态。
